# Reference data

This folder holds Jisr's curated reference data. It is the source of truth for the app; git history is the audit trail. It currently holds **no records**.

**Only records whose every value traces to an official https source belong here.** Never invent or fill in a value. If something is not published, write `null` and let the app show "to be checked".

## Layout

One record per file: `data/<collection>/**/<id>.yaml`.

- The collection is the first folder under `data/`. Deeper folders are organisational only.
- The file name (without `.yaml`) equals the record's id: `slug`, or `code` for `countries`.
- Do not rename a slug. Saved user data will refer to it, and the slug alias/redirect mechanism is not yet supported (to be built before accounts persist slugs, phase 2), so a rename breaks saved data.
- Use the `.yaml` extension. `README.md` and dotfiles are ignored; anything else is an error.

The 13 collections:

`countries`, `fields`, `subjects`, `language-certificates`, `grading-scales`, `grade-conversions`, `credential-types`, `application-channels`, `admission-routes`, `institutions`, `programs`, `cost-profiles`, `scholarships`.

## Provenance

Every record other than the vocabulary collections (`countries`, `fields`, `subjects`, `language-certificates`) has a `sources` map of `key -> { url, last_verified_at }`, and every fact, rule, requirements block or record-level claim names one of those keys in `source`.

- `url` is an official https page.
- `last_verified_at` is the date a human actually read that page (`YYYY-MM-DD`, never in the future).
- `info_kind` is `official`, `estimate` or `guidance`. An `estimate` also needs a `basis` explaining how the range was derived.
- A source key that is used but not declared is an error. A declared key that is never used is a warning.

## Tuition

A program has a `tuition` figure (one fee or an official range, ADR 0010), by convention the fee that applies to the Release 1 audience: students from outside the EU/EEA (for example Moroccan students). It must be an official published fee (`info_kind: official`); when the university does not publish one, leave the value `null` and the app shows it as to-be-checked. An estimate is never accepted here, because it would be turned into a single-number range. A range needs one quote that states both the lowest and the highest fee; `basis: income_based` only when the quote says the fee depends on income (for example the ISEE). Never an estimate.

## Intakes and deadlines

An intake has `startDate`, `applicationOpens` and `applicationDeadline`, each a full ISO date or `null`. When the official page gives the deadline as a day and a month with no year ("15 July"), do not guess a year: write it as `recurringDeadline: { month: 7, day: 15 }` and leave `applicationDeadline` as `null`. An intake never has both (`data:check` errors); the field is optional, so existing records stay valid. The app shows a recurring deadline as "usually by DD/MM each year, check the date for your intake", never as an upcoming date and never with a guessed year (ADR 0009). It is a volatile fact like any deadline (aging 120 days, stale 270). Only a deadline that applies to international or non-EU applicants belongs here; a general or EU deadline is left out.

## Checking

```
pnpm data:check              # validate every record, print freshness and translation reports
pnpm data:check --strict     # additionally fail when any fact is stale
pnpm data:build              # publish immutable JSON snapshots (runs after data:check)
```

`data:check` fails on invalid or provenance-less records, dangling references, unknown keys, future dates, a non-null program `tuition` that is not `official`, an invalid tuition range (maximum below the minimum, a basis without a maximum), and `complete` coverage with no rules. Aging and stale facts are reported, and only fail the run under `--strict`. It also warns (without failing) about unused sources, `complete` coverage with a `manual_check` rule, a `complete` program that has teaching languages but no `language_proficiency` rule, a `language_proficiency` rule that requires a certificate but lists no `acceptedTests`, and a cost profile whose `city` matches no institution city.

## Importing candidates (`data-staging/`)

Official bulk datasets are pulled into `data-staging/`, never straight into `data/`. A staged record has the exact shape of a `data/` record, plus a `_review` block, and every `last_verified_at` is `null`. Any fact the importer could not read (and any value it only guessed, such as a website from Wikidata) carries `info_kind: TODO_read_source`, which is deliberately not valid: `data:promote` refuses the record until a human has read the source and chosen a value, or an explicit `null` for "not published". `data-staging/` is committed as the review queue; it is not read by `data:check` or the build.

```
pnpm data:import france          # Parcoursup open data (Licence + BUT, CS/engineering/business) + institutions
pnpm data:import institutions    # German (HRK) and Dutch (DUO) institution candidates
pnpm data:import netherlands     # Dutch programmes (RIO register) and their campus institutions
pnpm data:import germany         # German programmes (Studiensuche API), linked to the HRK institutions
pnpm data:uniassist             # uni-assist university list -> data-staging/UNIASSIST.csv (which German universities use uni-assist, and how)
pnpm data:import daad            # English-taught German programmes (DAAD), with language, duration, deadline
pnpm data:import hungary         # English-taught Hungarian Bachelor programmes (Study Finder, Tempus Public Foundation) and their institutions
pnpm data:import italy           # English-taught Italian Bachelor programmes (MUR open data) and their universities, with website candidates
pnpm data:import                 # all sources; keeps staged files (--overwrite replaces them and clears their approval; --refresh bypasses the HTTP cache)
pnpm data:promote --confirm-human-read --verified-on YYYY-MM-DD
```

1. Open `data-staging/REVIEW.csv` (one row per record: name, institution, city, field, confidence, official link, what is still to check). Read the source, fix the staged YAML (replace each `TODO_read_source`, fill the website/type), then write `y` in the `approved` column. Re-importing never keeps an approval for a file it rewrote.
2. `data:promote` takes every approved row, stamps the date you pass as `last_verified_at` on every source, validates the record against its schema, and moves it into `data/`. A record that is still invalid is skipped and stays staged; an existing `data/` record is never overwritten. Pass the flags only after you have read the sources.
3. `pnpm data:check` then reports dangling references (promote a programme's institution too).

## uni-assist mapping (`pnpm data:uniassist`)

uni-assist e.V. is the central service many German universities use for applicants with a foreign
school-leaving certificate. Its official list (197 universities) says, per university, one of:

- **processes**: no note on its page: uni-assist handles the application;
- **vpd_only**: "We will issue you with a preliminary review documentation (VPD). You are then
  required to submit your application with the VPD directly to the university.";
- **special**: a note that only concerns some courses or levels (read it).

`data-staging/UNIASSIST.csv` has one row per university with the mode, the detail page (the source
to cite) and the note verbatim. Each row is matched to our German institutions by website host,
then registrable domain (language subdomains such as `en.w-hs.de`), narrowed by town for
universities with several campus units, then by exact normalised name. A row that matches nothing
is **never guessed**: `sameTownCandidates` lists our institutions in that town for a person to
decide. The page itself says that each university decides which courses and applicant groups
uni-assist handles, so the sheet narrows the question and the university's own page answers it.
Nothing in `data/` is written from this sheet yet.

## Trust tiers: how this scales past what a person can read

No team can read thousands of programmes, so the data does not pretend that someone did. Every record
carries a **tier** in the ledger (`data-staging/PROMOTED.csv`, column `level`), and the site only
claims "Official, verified" for a fact that has a source quote, never for an unknown.

| Tier (`level`) | What it means | Who or what checked it | Where it applies |
|---|---|---|---|
| `human` | a person read the sources | a person | records edited or sampled by the owner |
| `audited-sample` | prepared by the assistant with a verbatim quote per fact, in a batch whose random sample was read and passed | code (quotes re-fetched) + a sample read by a person | the pilot flow (`data:evidence`, `data:audit`) |
| `owner-waived` | same preparation, but the owner passed the sample **unread** (a preview) | code only | the 15-programme pilot, today |
| `register-listing` | only what an official register states: name, institution, town, field, level and a link to the official page; **every other fact is "to be checked"** | the schema, `data:check` and the link check below | France (Parcoursup) and Germany (DAAD) listings, `pnpm data:listing` |
| `machine-quoted` | a listing plus facts that code read from the official page and quoted verbatim, each re-fetched and checked by the same verifier as the pilot | code (extractor + verifier) | French listings: `pnpm data:enrich-fr` (French level required, distance learning, and the national facts below) |
| `demoted` | a listed record whose official page no longer shows its name went back to staging | `pnpm data:linkcheck --demote` | any listed record |

Principles:

1. **Never show a "verified" label next to an unknown.** A value nobody has read shows "to be checked" and
   no badge (ADR 0005 item 9). An institution whose type or website the register does not state keeps
   `type: null` / `website: null` instead of a guess.
2. **Verify the process, sample the output, test everything cheaply.** Register-derived records come from
   a deterministic importer, so the error rate is a property of the importer, not of each record.
   `pnpm data:linkcheck` fetches every listed programme's official page and requires it to mention the
   programme's name (all 915 listings: 891 pass, 24 were demoted; run it again to catch pages that move).
3. **Depth comes in small batches.** Quote-verified facts (`data:evidence`) are added per batch, starting
   with the shortlist (`data:shortlist`), and each batch has its own audit sample.
4. **Keep checking.** `data:evidence verify --dry-run` re-fetches every quote of the promoted records and
   reports the ones that no longer match; `data:uniassist` and `data:linkcheck` can be re-run the same way.
5. **Records the importer cannot support stay in staging** (low-confidence field classification,
   institutions not in an official register, programmes without an official page link).

Listing tier details: the DAAD duration and teaching language are taken as `guidance` (DAAD is a listing
service, not the institution); its deadline is never used (it can be the one for EU applicants). A French
institution's website is listed only when the ministry's register confirmed it; a German one only when the
HRK homepage does not redirect to another domain. The date in `last_verified_at` is the day the register
was read by code, not a day a person read the record.

### French machine-quoted facts (`pnpm data:enrich-fr`)

For every French listing the extractor adds only what an official page states, with its quote:

- **French level required** (and the mandatory TCF / DELF-DALF certificate): the Parcoursup fiche says "Niveau de français requis pour s'inscrire à la formation : B2" (754 of 757 fiches state a level); Campus France Maroc says the certificate is mandatory unless exempt.
- **Distance learning**: the fiche's own sentence.
- **Duration**: Campus France's national pages (a Licence is "six semestres", the BUT is "préparé en 3 ans").
- **Tuition for a student from outside the EU** at a public institution: Campus France Maroc ("2 902 euros pour une année en cycle de Licence"); a note says some institutions exempt non-EU students. The 178 euros shown on every fiche is the EU rate and is never used.
- **Application platform**: Études en France, from the Campus France Maroc Licence and BUT pages.

National facts are not the programme's own page: the badge shows the Campus France page as their source. Teaching language, deadlines and documents stay "to be checked": the fiche has no clear sentence for them (its "Langue vivante 1" is a school-subject requirement, not the teaching language).

## Reading pages with cheap models (OpenCode Go)

Per-programme reading by Claude is replaced by cheap models called from scripts (they bill OpenCode, not Claude). The trust model does not change: a model only *proposes*; code decides.

```
pages we fetched ──► reader (cheap model) ──► ProposalSchema ──► verifyProposal (code: quote on page? value agrees?)
                                                                      │
                                       checker (strong model, claim + ~500 chars; --check) ──► proposals-read/<slug>.json
                                                                      │   (copy to proposals/, then data:evidence verify ──► audit sample ──► promote)
```

`data:read` writes proposals into `data-staging/proposals-read/` only. Nothing is applied to staged records, no date is stamped and nothing is promoted by these scripts: the existing `data:evidence verify`, `data:audit` and `data:promote` steps stay the only way in. With `--check`, what the checker removed is also removed from the saved proposal, so a later `data:evidence verify` cannot bring it back. Evidence that cites a page the reader was not given (one it remembered, an aggregator) is dropped before verification, and a fact left with no evidence is dropped with it (listed under `dropped` in `calls.jsonl`).

- `scripts/import/llm.ts`: the OpenCode client (three wire formats, streaming, price table, idle watchdog). Key from `OPENCODE_API_KEY` (env or `.env.local`, never committed, logged or echoed in errors). The hard `Budget` cap reserves each call's worst case before it is sent, so parallel calls cannot overshoot it; a stream without usage is charged an estimate.
- `scripts/import/reader.ts` (`pnpm data:read`): prompt = fixed instruction + shared national pages first (cache hit), the programme's pages last. A badly formed fact or rule is dropped and counted (`dropped`), never passed on without evidence; a language rule with unknown `acceptedTests` is dropped (an empty list means "any certificate"). The French application channel is left to the route data. Every command has `--dry-run` and `--max-usd`.
- `scripts/import/checker.ts`: the second model judges whether the quote states each fact and each requirement rule *for this programme and a Moroccan, non-EU applicant*. It can only remove; an unusable answer removes all facts and judged rules (fail closed); a `manual_check` note is not judged and the programme page is checked by code. A budget stop stops the run.
- `scripts/import/discover.ts`: finding the pages. `discoverFromRegister` reads a register page that links the programme's own page ("Course website" on DAAD pages, plus the fee and application links) and works for Germany; `discover` crawls from the institution website and is only a weak fallback (it found the exact pilot page for 2 of 14).
- Deadlines (ADR 0009): the reader writes an application deadline as a dated `applicationDeadline` only when the quote states the year, and as `recurringDeadline` `{month, day}` only when it states day and month with no year; never both on one intake. `verifyProposal` checks a dated deadline against the quote as before, and a recurring one with `checkRecurringDeadline`: the day must stand beside the month in an accepted quote, and a quote that contains a year is rejected for it (it is a dated deadline, not "every year"). Every application deadline, dated or recurring, also needs an accepted quote that names international or non-EU applicants (`mentionsInternationalApplicants` in `scripts/import/evidence.ts`: English, German, Dutch and French phrasings such as "non-EU", "nicht-EU", "buiten de EU", "hors UE", "third country", "international", "foreign", "from abroad"; programme and office names such as "International Business" or "International Office" do not count). Without such a quote the deadline is rejected and the intake fact is not accepted. The word check is only a first filter: the checker model (`--check`) judges the claim for an international applicant and the audit sample reads it.
- The international rule is not retroactive. Deadlines already in `data/` are kept as they are. Re-running `data:evidence verify` on an older proposal may now reject a deadline that was promoted earlier; do not remove it automatically, list such records and let the owner decide. Enrichment never overwrites an existing official value, so a rejected or new deadline does not replace one already in `data/`.
- `pnpm data:bakeoff` / `pnpm data:checkeval`: model comparison on the 15 pilot programmes against the quote-verified pilot proposals.

Bake-off result (2026-10-01, prompt v2, 40 truth facts, same pages for every model): readers DeepSeek V4.1 Flash, GPT 6 Luna, Hy3, Qwen3.8 Flash and MiMo-V2.6-Flash all agree with the truth on 29-31 facts with 0-2 wrong-but-verified (conflict); about 0.1-0.3 cent per programme. GLM-5.3-Flash and Kimi K2.7 Code reason for thousands of tokens and are not usable as readers; LongCat Free is too slow. As checker, Qwen3.7-Plus removed 4 of 4 wrong facts and kept 31 of 35 correct ones (the 4 it drops are strict "not stated for non-EU / only recommended" calls) at about 0.3 cent per call; Kimi K2.7 Code and GLM-5.2 return unusable answers more often. Muse Spark needs "models that train on request data" enabled in the OpenCode privacy settings and was not used.

### Topic pages, PDFs, documents and enrichment

- `pnpm data:pages --slugs <file> --search --topics` builds the pages file for `data:read`. `--topics` adds, per institution, the pages found by four searches restricted to its site (fees, language of instruction, deadline, documents; German, French or Dutch wording, by the programme's country) to every programme of that institution: one query per topic per institution, not per programme. It needs the same key as `--search` (`SERPER_API_KEY` or `BRAVE_API_KEY`) and is bounded by `--max-queries`. PDFs are kept (fee schedules); other file types and dated news posts are not. The programme's own pages stay first and are never dropped: "at most 10 pages" limits the topic pages that are added (they fill what is left up to 10 in total). A topic search that fails for one programme is logged (`topic search failed for <slug>`) and that programme keeps its existing pages; the run summary counts these and the programmes skipped because their institution has no https website, and lists those slugs in `<out>.skipped.txt`. A wrong topic page costs tokens only: the reader still has to quote it and the verifier still has to find the quote.
- `--dry-run` sends no search query and writes nothing, and prints the upper bound on queries, but it is not offline: it still fetches the DAAD register page of every German programme, and a dry run without `--search` also crawls the institution homepages of the programmes that have no register page or Parcoursup fiche.
- PDF text (`scripts/import/pdf.ts`, `unpdf`): a URL whose path ends in `.pdf`, or any page whose body turns out to be a PDF (a `/download?id=3` link), is read as text, cached next to the HTML cache, and the reader and the verifier see exactly the same text. A body that is neither text nor a PDF (more than 1% replacement characters) is refused, never sent to the reader. The limit is 8 MB; there is no OCR, so a scanned PDF (no extractable text) is reported like a page that cannot be fetched.
- The `documents` fact is the list of documents an international applicant must submit. Each item has a slug, a name (`fr`, `en`), `quotedAs` (the name exactly as the page writes it, in the page's language) and `translationRequired` (`true` or `null`, never `false`). `verifyProposal` keeps an item only if its `quotedAs` is found, as a whole word, in an accepted quote ("ID" is not found in "valid"), and keeps `translationRequired: true` only if a quote that names that same document also mentions a translation; otherwise it becomes `null`. If no document is named in a quote the whole fact is rejected. A quote naming several documents and mentioning translation supports all of them, so the checker model (`--check`) judges whether it really applies to each.
- Enrichment adds facts to records already in `data/` without resetting anything. `pnpm data:evidence restage --enrich <dir>` brings the records that have a proposal with facts in `<dir>` (for example `data-staging/proposals-enrich`, or one run directory `data-staging/proposals-read/<run>`: `proposals-read` itself holds run subdirectories, not proposals) back into staging, keeping their dates, marked `_review.enrich: true`. `pnpm data:evidence verify --enrich <dir>` verifies those proposals and touches only the marked records. `restage --enrich` always needs `--slugs <file>`, drops the audit rows of the records it restages (they go through a new audit batch) and skips a slug that already has a staged file, printing `already staged, skipped: <slug>`. A plain `verify` (without `--enrich`) skips records marked for enrichment and prints `skipped (restaged for enrichment: use --enrich): <slug>`. Enrichment fills a fact only where the record has no official value; it never overwrites an official value (a disagreement is recorded in the review notes instead), and when the programme page was not verified it never replaces any existing value either, only fills a missing one (a non-null register value is kept and the reader's competing value and url go into the review notes) and never touches requirements, the official URL, the summary or the scholarships. The output says `page NOT verified` when the programme page itself was not confirmed (the facts then come from pages not tied to the programme by name, and the record carries a note saying so), `no new facts: discard the staged revision for <slug>` when nothing was added, and `no further facts ... (earlier enrichment kept)` when the staged copy already holds earlier enrichment. Enriched records go through `data:audit` and are promoted with `--replace-revisions` like any revision.
- `pnpm data:coverage` prints a markdown table, one column per country, of how many programmes in `data/programs` hold each fact (programmes, tuition, tuition official, teaching language, intakes, application channel, documents, duration, programmes with at least one requirement rule). A null or empty fact does not count. It reads `data/` only, uses no network and writes nothing.
- `pnpm data:coverage --detail [--out <file>] [--csv <file>]` lists the same facts per institution (grouped by country, then name, with its slug): programmes, programmes holding each fact, programmes holding all of them, then each programme missing something with the names of the missing facts. "deadline" is an extra fact: an intake with an application date or a recurring one. `--csv` writes one 0/1 row per programme (with `missing_count`); `--out` needs `--detail`. Files are written only when `--out` or `--csv` is given.
- `--topic-list <a,b>` narrows `--topics` to a subset of `fees,language,deadline,documents` (default all four). It needs `--topics` (alone it would silently do nothing, so `data:pages` stops with an error), an unknown name is an error, and the `--dry-run` query bound counts only the chosen topics.
- Study-year gate and institution-wide Dutch fees (run 3): `checkTuition` refuses an amount that its quote ties to a study year before the current one (`currentStudyYear`: from August on, this calendar year). Each occurrence of the amount takes the closest study-year label written before it (else the first after it); years that stand side by side as column headers ("2025-2026 2026-2027 ... € 10.164 € 10.528") are ambiguous and refused unless all are current; dates, spans of years and "seit/since/sinds" labels are not study years; a quote with no study year is not judged by this gate (read those closely in the audit). `verifyProposal` takes the minimum study year as a fourth argument (default: the current one). The NL country note in `reader.ts` lets the reader use an institution-wide fee page for a bachelor programme (owner decision, strict conditions): one non-EU instellingscollegegeld amount for bachelor or all programmes, in the same quote as the study year and full-time/all modes, never the wettelijk collegegeld, never an exception-list programme, a fee on the programme page wins, and two quotes (who pays it, and the amount with the year). The checker is unchanged and still drops what the excerpt does not state for a non-EU applicant.
- Fee-link following: when the fees topic finds pages, `followFeeLinks` (`scripts/import/topics.ts`) fetches at most 3 of them (never a PDF) and adds up to 2 links found there: https, same site as the institution, not news or a dated post, scoring as a fee link, and naming a study year ("2026-2027", "2026/27", "studiejaar", "academic year") or a fee tool (collegegeldmeter, tarieven, fee calculator). Only the newest study year found on any of the pages survives and sorts first, so a past year's rate sheet never outranks the current one; undated links stay. PDF links are returned but never fetched here (the reader and verifier read them as above). A page that cannot be fetched is skipped, and a URL is fetched once per run, shared by the programmes of an institution.

### National calendar (France, `pnpm data:fr-calendar`)

Campus France Maroc publishes one application calendar per kind of programme as a sentence on its Études en France application pages ("Du 1er octobre 2026 au 15 novembre 2026 à 23h59 (heure marocaine)"). `pnpm data:fr-calendar` reads the BUT page and the 2026/27 calendar page, turns that sentence into an intake-only proposal (`applicationOpens`, `applicationDeadline`, `startDate: null`) for every French BUT programme and every Licence programme (not a Licence professionnelle), and writes one `<slug>.json` per programme into `data-staging/proposals-fr-calendar/`. The dates are parsed from the sentence by code, never typed; an impossible date, or a range that ends before it starts, gives no proposal. A second quote says whom the application is for, and it depends on the kind: the Bac marocain sentence for a BUT, the `DAP blanche : 1ère année de Licence à l'Université (L1)` line (same calendar page) for a Licence. Only programmes of a public institution (`type: public` in `data/institutions/<slug>.yaml`) get a proposal: private institutions and programmes whose institution record is missing are skipped, and the summary counts them and lists their names. No model is called and nothing is applied to `data/`: the proposals go through the existing enrichment flow, `pnpm data:evidence restage --enrich data-staging/proposals-fr-calendar --slugs <file>`, then `verify --enrich`, `data:audit` and `data:promote --replace-revisions`, and the deadline rules above (an accepted quote must name international applicants) still apply.

- `--dry-run` computes everything and writes nothing. The summary counts the BUT and Licence programmes that would get a proposal and prints the calendar sentence found for each kind, or "no calendar sentence found".
- A programme that is neither a BUT nor a Licence (a Master, an engineering diploma) gets no proposal.
- The Licence calendar comes from the Campus France Maroc 2026/27 calendar page (`PAGES.calendarLicence`, `scripts/import/enrich-fr.ts`), which states one window for the connected formations including first-year Licence. A Licence proposal cites two quotes from that page: the date sentence and the `DAP blanche : 1ère année de Licence à l'Université (L1)` line that says who it is for; if that line is missing, or the page carries more than one distinct date sentence, there is no Licence proposal (the summary prints a note).
- Proposal files in the output directory that an earlier run wrote and this run did not are listed in a warning, never deleted.

### German deadlines from the DAAD register (`pnpm data:daad-deadlines`)

The DAAD register page of a programme prints its application periods in a fixed shape: `Application periods The following is valid for applicants from: all countries For the winter semester: until 15 July`. "All countries" (or "non-EU countries") includes a Moroccan applicant, so `mentionsInternationalApplicants` accepts `applicants from: all countries` as international wording. `pnpm data:daad-deadlines [--dry-run]` reads that block by code for every German programme whose programme page is a DAAD register page and that holds no intake yet (enrichment never replaces an official value, so a record with intakes but no deadline cannot take one), and writes one intake-only proposal per programme into `data-staging/proposals-de-deadlines/` (no model, no search credits; the DAAD pages come from the fetch cache or one polite request each). Rules: only a winter-semester period or an unlabelled one counts (a summer-only block gives nothing, because an intake has no semester label); only the audiences `all countries` and `non-EU countries` count (an EU-only block gives nothing); the deadline is the `until` date or the end of a range; no year in the page gives a recurring deadline, a year gives a dated one and never a guessed one; a dated deadline that is already past is skipped; two different qualifying deadlines on one page are ambiguous and skipped; free text ("Mid-May until mid-September", "end of June", "uni-assist: 1 May - 30 June") is not parsed and stays unknown. The quote is the whole `The following is valid for applicants from: ...` piece for that period, re-fetched by `verifyProposal` like any quote. The proposals go through `restage --enrich`, `verify --enrich`, `data:audit` and `data:promote --replace-revisions` exactly like the France calendar.

### National facts (`pnpm data:national`)

Some documents and application-channel facts are stated once, nationally, for hundreds of programmes (the Campus France Maroc dossier, the uni-assist lists, Studielink, Universitaly). `pnpm data:national <registry.json>... [--dry-run] [--out <dir>] [--data-dir <dir>] [--uniassist-sheet <csv>]` turns curated registry files (`scripts/import/registries/national-*.json`) into one proposal per selected programme, with no model and no search credits. A registry is `{ "entries": [...] }`; an entry has an `id` (kebab-case, unique across files), a `fact` (`documents` with `items`, or `applicationChannel` with a `channel` slug), an `infoKind` (`official` or `guidance`: a page that only says documents are "normally" or "often" required is `guidance`), a `selector`, `evidence` (https `url` and a verbatim `quote` of at least 15 characters, re-fetched by the verifier) and optional `notes` (shown to the auditor in the review notes). A document item is `{ slug, name: { fr, en? }, quotedAs, translationRequired }`: `quotedAs` is the name exactly as the quote writes it, and `translationRequired` is `true` or `null`, never `false`. A selector is a conjunction of `country` (required), `institutions` (slugs), `programmes` (programme slugs: use it when a quote is about one programme and the institution has others without that fact; a slug no programme has is reported as a warning), `institutionType` (`public` or `private`; a programme whose institution type is unknown never matches), `kinds` (French only: `but`, `licence`, `other`) and `channels` (the programme's current channel).

- `--uniassist-sheet data-staging/UNIASSIST.csv` (written by the uni-assist import) appends one `de-uni-assist-vpd` channel entry per sheet row whose mode is `vpd_only` and that matched an institution of ours: the quote is the VPD sentence of the row's note and the evidence url is the uni-assist detail page, which the verifier re-fetches like any quote. Rows with mode `processes` or `special`, unmatched rows and notes without VPD wording are never proposed; they are printed as a list left for a person (a `processes` university needs a quote from its own page, in a registry).
- It never overwrites an existing value: a programme that already holds the fact is skipped and counted. Two entries for the same programme merge into one proposal file; a second claim on the same fact is skipped (the first entry wins).
- Each entry is verified once with `verifyProposal` (national evidence is identical for every programme). A rejected fact proposes nothing and prints the reason: a quote that fails is a registry bug. A fact is also refused when any of its quotes is missing from its page (an unfound quote would be carried into every proposal), when a cited page cannot be fetched (`page could not be fetched: <url>`), and the whole run stops at an HTTP 403 or 429. A document item named in no quote, or a `translationRequired: true` the verifier turns into null, is printed as a warning. A registry with a misspelt key (any object is strict) is refused.
- It writes `<slug>.json` plus a sorted `slugs.txt` into `data-staging/proposals-national/<registry name>/` (or `--out`); `--dry-run` writes nothing. Files left by an earlier run are listed in a warning, never deleted. The summary prints, per entry, selected / proposed / skipped / rejected, with warnings and totals, then the three next commands (none when nothing was proposed, and then no `slugs.txt` is written):

```
pnpm data:evidence restage --enrich <out> --slugs <out>/slugs.txt
pnpm data:evidence verify --enrich <out> --slugs <out>/slugs.txt --dry-run
pnpm data:evidence verify --enrich <out> --slugs <out>/slugs.txt
```

The proposals then go through `data:audit` and `data:promote` like every other enrichment.

Audit sampling for national batches (owner decision, 2026-10-09). `data:audit draw` normally samples `max(10, 10%)` of a batch. When every record of a batch has an evidence log (`_review.evidence`) made of the same set of fact/url/quote triples (compared without regard to order) and holds the same value and info_kind for every fact the log names (`isIdenticalEvidenceBatch` in `scripts/import/audit.ts`; the source key is not compared) and the batch has more than 12 records, the sample is 12, drawn with the same seed rule: the records only repeat one national page, so a person reads that page once. There is no flag; any record with a different or extra quote, a batch of 12 or fewer, and anything containing scholarships or official cost profiles (always 100% audited) keep the ordinary rule. `data:audit sheet` then headlines the batch ("identical national evidence: sample of 12 of N; the national page is read once") and prints the shared quotes and urls once at the top; it recognises the batch from the records still in staging, so after a partial promotion it falls back to the ordinary header. Under that headline it prints one composition line over all the records of the batch (counts by country, institution type, French programme kind, current application channel, and the number of distinct institutions), so the reader sees at a glance whether a selector took in programmes the page is not about.

### Italy pages file from the curated registry (`pnpm data:it-pages`)

`pnpm data:it-pages --registry <file[,file...]> --out <pages.json> [--max-per-programme 14] [--data-dir data]` turns the curated Italy page registry (one JSON file per research batch: per university the admissions, fees, country-list, documents and language pages, and per programme its own pages) into the pages file that `pnpm data:read --pages` takes, in place of the automatic search of `data:pages`, which found wrong pages for Italy. ### Official cost profiles (`pnpm data:costs-official`)

Living costs come from the figures official bodies publish. The assistant writes a proposal from the official pages, and code decides what is kept; every line carries a verbatim quote.

```
pnpm data:costs-official verify <proposal.json> [--dry-run] [--delay-ms 4000] [--use-cache]
```

Flow: proposal JSON (`data-staging/proposals-cost-official/<cc>.json`) -> `verify` -> staged profile (`data-staging/cost-profiles/<cc>-official.yaml`; a city profile is `<cc>-<city>-official`, and version 1 has only `fr-paris-official`) -> audit sheet -> `data:promote`. The proposal (`OfficialCostProposalSchema` in `scripts/import/official-costs.ts`) has `slug`, `country`, `city` (a slug or `null`) and up to one line per category (housing, food, transport, insurance, application_visa, setup), each with `min`, `max` (major units, converted with `minorUnitDigits`), `currency`, `per` (`month`, `year` or `once`), `info_kind` (`official` or `estimate`), a trilingual `basis` (required for an estimate) and `evidence` (`url`, `quote`, optional `dateQuote`). Staging is never overwritten (a staged file or a slug already in `data/` stops the run), and `--dry-run` writes nothing. `--use-cache` reads a page already on disk instead of requesting it again; a cached page may date a past reading, so the report says so.

What `verify` checks, per line (a line that fails is dropped alone and reported; a profile with no kept line is not staged):

- **Host:** the url must be on the official allowlist (`isOfficialHost` in `scripts/import/scholarships.ts`: the provider's own site, DAAD, Nuffic, Campus France, government sites).
- **Quote:** it must be on the freshly fetched page, verbatim (whitespace and case normalised, 15 characters at least).
- **Numbers and currency:** every number of `min` and `max` must be in the quote, written with the currency next to it, with no thousands-separator mix-up (1.2 is not in "1.200", 40 is not in 400 or 1 500).
- **Age (estimates and official lines):** `MIN_ESTIMATE_YEAR = 2026` (owner decision 2026-10-07: only 2026 figures), judged on the years in the quote (the oldest one decides; an amount such as "2040 EUR" is not a year). `dateQuote`, a second verbatim quote from the same page, counts only when the quote has no year, and the audit sheet shows it. It dates the page, not the figure, so the 100% audit must still read the figure; the report and the review notes say so. An `official` line is judged the same way: a line with no 2026 year in its quote or `dateQuote` is dropped.
- **Period:** `per` must not contradict the nearest period word in the quote (English, French, German, Italian, Hungarian and Dutch words). A duration phrase such as "inferiore o pari a un anno" is not a period and is ignored with a note. A quote with no period word is accepted with a note that `per` comes from the proposal.
- **Politeness:** one request at a time, at least 2 s apart (default 4 s), one attempt, the project User-Agent. The run stops on the first HTTP 403 or 429 and stages nothing; an unfetchable page (other errors) drops its line.
- **Single figure:** a figure published once is stored as `min = max`; a published range is stored as the range. Never an invented spread.

The audit sheet always includes official cost profiles (100%, never waivable, like scholarships), because a model prepared the quotes. The coupling to know: a quote without a period word is only safe because every official profile is read by a person.

### Numbeo cost profiles (parked)

`pnpm data:costs` is built and tested but PARKED. Numbeo answered HTTP 429 from about the 15th page of the run on 2026-10-05 (the first version had no circuit breaker: 289 requests were rejected), the block lasted over 11 hours, and the owner decided on 2026-10-06 to use official sources instead. The 20 staged profiles are in `data-staging/parked-numbeo/` and are never promoted: Numbeo figures are not shown or stored (there are no official living-cost profiles for DE, NL and IT since 2026-10-07, but the owner chose a link to Numbeo over its figures). Do not re-run the scrape unless Numbeo grants access (an allowlist or an export); if it does, the same audit path applies, with the normal 10% sampling for those profiles. The rest of this section documents the code as built.

Living costs are monthly estimates from Numbeo's cost-of-living pages, read by code (a deterministic table parser, no model, no search credits). The owner holds Numbeo's written permission (see the licence table); the scrape was meant to be one-off.

```
pnpm data:costs [--dry-run] [--countries FR,DE,...] [--max-requests 400] [--delay-ms 8000]
```

It stages `data-staging/cost-profiles/<cc>-<city-slug>-numbeo.yaml` for every programme city in `data/` (the city name comes from the programme's institution) and `<cc>-numbeo` for every country, which is the fallback for a city without a usable profile. A staged file or a slug already in `data/` is never overwritten. Requests are sequential, at least `--delay-ms` apart (default 8000, 2000 is the minimum), one attempt each with no retry, cached in `.cache/import/` (a re-run costs no request for a cached page), capped by `--max-requests`; a URL disallowed by robots.txt is refused. `--dry-run` prints the number of requests and the time they would take, and fetches and writes nothing; `--countries` limits the run (default FR, DE, NL, IT, HU). A failed fetch is reported and the command exits 1; re-run to retry it. A city is asked for as `<City>-<Country>` and, if Numbeo answers "Cannot find city id", as the bare name (a second counted request); the page's breadcrumb must name the expected country. The first HTTP 429 or 403, or 3 failures in a row that are not 404 (network, timeout, 5xx, a 200 page that is not a Numbeo cost page, which is never cached), stops the whole run at once (the rest is listed as not fetched, exit 1): wait before re-running.

- **Which page.** Numbeo serves some cities only bare (`/cost-of-living/in/Dresden`) and others only as `Name-Country` (`/cost-of-living/in/Agen-France`); the other form answers 200 "Cannot find city id". The code asks for `Name-Country` first, then the bare name (a second counted request); a form already in the cache is tried first because it costs no request. "Cannot find city id" on both forms, or a 404, counts as "not listed" and the city falls back to the country profile; so does a page with no usable line.
- **Identity guard.** The page's h1 ("Cost of Living in ...") must be the asked-for city or country (accents and punctuation ignored); for a city page the breadcrumb country must equal the expected country; and the currency symbol of the first price cell must be the asked-for currency (`€`; `Ft` or `HUF`). Otherwise nothing is staged: for a name it does not know Numbeo answers 200 "Cannot find city id" (not a redirect), and it ignores a currency it does not support.
- **Currency.** EUR for France, Germany, the Netherlands and Italy; HUF for Hungary, as Numbeo prints it, never converted. Money is integer minor units, and the number of digits is pinned per currency in `src/lib/format.ts` (EUR 2, MAD 2, USD 2, HUF 0), so HUF is stored in whole forints, unlike ISO 4217's 2 digits.
- **Housing** is the low to high range of the row `1 Bedroom Apartment Outside of City Centre`. No range (a missing end, or low above high) or a row listed twice gives no line, never a single value.
- **Food** is a fixed monthly basket for one student, each row times its quantity: milk 8 L, bread 8 loaves (500 g), rice 2 kg, eggs 24 (two 12-packs), chicken fillets 3 kg, apples 3 kg, bananas 3 kg, tomatoes 3 kg, potatoes 4 kg, onions 2 kg, lettuce 4, 8 meals at an inexpensive restaurant. Min is the sum of the rows' low prices and max the sum of the high prices. Any basket row missing, repeated or without a range gives no food line. The basket is our modelling choice and is listed in full in the line's basis, in all three locales.
- **Transport** is the range of the row `Monthly Public Transport Pass (Regular Price)`; a student pass may cost less (not modelled).
- **Rounding.** Sums are taken in hundredths, then min is rounded down and max up to whole units (outwards: the range never shrinks) before conversion to minor units. A row the page does not list gives no line, and a profile with no line at all is not staged; a staged profile with a missing line prints a `partial` line naming the rows not built, repeated in its `_review.notes`.
- **Trust.** Every line is `source: numbeo`, `info_kind: estimate`, never `official`, with a trilingual `basis` (all `draft`) that says it is crowdsourced and unofficial, gives the page's last-update date and its number of contributors, and states the formula. A page that carries Numbeo's low-contributor warning ("Some data are estimated due to a low number of contributors") is flagged in `_review.notes`; its contributors count is in the basis.
- **Country profiles** are country-level figures: the range spans all of the country's cities, so it is wide, and its basis says it is used where the city has no usable Numbeo figure.
- **Audit and promote.** The profiles go through the normal audit sampling (`data:audit draw`, about 10% of the batch with a minimum; the sample sheet shows each line's range, the Numbeo rows behind it (average, low and high for housing and transport; low and high for each basket row of food), the formula, and the page to open) and then `data:promote --confirm-human-read --verified-on YYYY-MM-DD --audited-batch`, which stamps `last_verified_at` on the Numbeo source. The owner reads the sample before anything is promoted; staged records for held-out programmes and institutions (as in the other sections) are moved aside before the draw and before the promote. The credit "Numbeo, numbeo.com" must be shown wherever the figures are shown (licence table).

### Scholarships (`pnpm data:scholarship`)

Scholarships are Bachelor-level (`level: bachelor`; a scheme that covers Bachelor and Master is kept, see Level below) and verified-only. The assistant prepares a proposal from the provider's official pages; code re-fetches every cited page and decides what is kept, and a fact no accepted quote supports stays unknown (`null`).

```
pnpm data:scholarship verify <proposal.json> [--dry-run]
```

The proposal (`ScholarshipProposalSchema` in `scripts/import/scholarships.ts`) is JSON with `slug`, `name`, `provider`, `destinations` and `eligibleNationalities` (country codes; an empty nationality list means any international applicant), `fields` (empty = all fields), optional `institutions`, `summary` and `howToApply` (`fr` required, `en` optional), `officialUrl` (https), `support` (`amount` in whole major units with `currency` and `per` of month, year, once or total, plus `covers`; or `null`), `deadline` (ISO date or `null`), `documents` (or `null`) and `evidence`: verbatim `{ url, quote }` lists for `eligibility`, `level`, `howToApply` and optionally `support` and `deadline`. A quote counts only if it is on the cited page and on an official site (the provider's own, `daad.de`, `nuffic.nl`, `studyinholland.nl`, `campusfrance.org`, or a government site such as `gouv.fr`, `bund.de`, `overheid.nl`, `government.nl`, `.gov`). Then:

- **Eligibility:** an accepted quote must name international (non-EU) applicants; a quote that states an exclusion ("not eligible", "instead", "only EU citizens", ...) is dropped. Each listed nationality needs a quote that names the country or its region. The quote table (`NATIONALITY_NAMES`) covers MA, DZ and TN only; any other code is rejected until its names are added.
- **Level:** a quote must say the scholarship itself is for Bachelor (undergraduate, first-degree) students. A scheme that covers both levels is accepted too, because Jisr shows it only on Bachelor programmes: a quote that lists Bachelor as a covered level next to Master ("bachelor's or master's", "Bachelor- und Masterstudiengänge", "licence ou master", "bachelor/master") counts as level evidence. The Master word takes only a study suffix with it ("students", "programmes", "Studiengänge", "opleiding"); it does not count when the quote has prerequisite wording ("hold a Bachelor", "Bachelor graduates", "Bachelor's degree required"), any degree-possession word next to the levels ("Bachelor and Master graduates", "who have completed a first degree", "degree-holders", "already hold", "previous degree", "recipients", "alumni", "Absolventen", "diplômés", "obtenu", "postdocs", "Abschluss") or other Master-only or doctoral wording. A quote that makes it a Master-only or doctoral scholarship, or that requires a Bachelor's degree to apply (or is for its graduates), rejects the record. The audit sheet asks the auditor to confirm that a both-levels scheme is open to Bachelor students and not only to Bachelor graduates.
- **Support:** the amount is kept only if one quote states it as a whole number with the currency next to it and the period (per month, per year, one-time, in total) beside it; a ceiling ("up to") or a Master's amount does not count. In a clause that names Bachelor and Master together, the amount is kept only when it is the only amount in that clause (it then applies to both levels); with two amounts there, when the clause names Master only, or when it adds graduates or alumni, it is dropped. For a one-time amount the period may sit in the next sentence only when the amount's own sentence has no period word at all (monthly, annual, each, every, per, month, year ...) and the next sentence is nothing but "You will receive this" or "You will receive it", "in the first year", "for one year only" or "one-time", and at most "of your studies" ("The scholarship amounts to EUR 5,000. You will receive this in the first year of your studies."); anything else in that sentence (ten parts, per trimester, renewable, "and again", another number ...) means no period is read. Otherwise `support` stays unknown, with a note. `covers` keeps only what a quote names; `other` is never kept.
- **Deadline:** kept only if one clause of an accepted quote names international applicants, contains exactly one date and says what the date is (a deadline word, not an opening or results date). A quote with several dates (one per applicant group) leaves the deadline unknown.
- **Documents:** an item is kept only if an accepted quote names it as the page writes it; `translationRequired: true` needs a quote that also mentions translation, else it becomes `null`.
- **Institutions:** each slug must be a file in `data/institutions/`.

The record is staged in `data-staging/scholarships/<slug>.yaml` with its evidence and the rejected facts in `_review`; a staged file or a slug already in `data/` is never overwritten, and `--dry-run` writes nothing. Scholarships are few and shown as facts about money and eligibility, so `data:audit` always puts every `scholarships/*` item in the sample (`drawBatch`): they are 100% audited, whatever the batch size, and the audit cannot be waived for them (a `waived` outcome on a scholarship counts as still to read; only `ok` passes). The sample sheet spells out destinations, nationalities, fields and institutions ("ALL FIELDS", "ALL INSTITUTIONS") and the checks to confirm. After the audit, `data:promote` as for any prepared record.

Italian and "everyone" wording (Italy, Deutschlandstipendium): the verifier also reads Italian (international applicants: studenti stranieri, extra UE, non comunitari, studenti internazionali; undergraduate: corsi di laurea but not laurea magistrale, laurea triennale, primo livello; a list of first- and second-level courses counts as both levels; graduate or degree-holder wording such as laurea magistrale, specialistica, secondo livello, dottorato, laureati, conseguito la laurea rejects; Italian exclusions such as non può, esclusi, riservata ai ... drop a quote). Two narrow rules: "all nationalities" (not "except ...") counts as open to international applicants, and "every course of study is eligible" / "jedes Studium ist förderungsfähig" counts as covering the first degree (never when negated, when it only applies after the first degree, or when the same quote names master). Italian regional right-to-study grants (DSU) are one record per agency with `institutions` = the agency's region's universities; amounts are ISEE bands, so `support.amount` stays unknown.

The optional `institutions` field restricts a scholarship to the programmes of the named institutions (slugs of `data/institutions/`, checked by `data:check`). Absent or empty means no restriction. How a scholarship is matched to a programme: the student's nationality is filtered first (an empty `eligibleNationalities` matches any), a scholarship the programme links explicitly always applies, and otherwise the destination must match, `fields` must be empty or include the programme's field, and `institutions` must be empty or include its institution.

### Arabic translations (`pnpm data:translate-ar`)

Most `LocalizedText` nodes lack `ar`, but the same French texts repeat (document names on hundreds of programmes), so Arabic is filled from a reviewed dictionary, `scripts/import/translations/ar.json`: `{ "entries": [ { "fr": "<exact French text>", "ar": "<Arabic>", "status": "draft" | "reviewed" } ] }`, unique by `fr`, strict Zod schema, `ar` must contain Arabic letters, `status` defaults to `draft`. A machine-drafted entry is `draft`; the owner's review makes it `reviewed`.

```
pnpm data:translate-ar export [--out <file>]      # unique French texts without ar -> data-staging/translations/ar-todo.json + ar-todo-batch-<n>.json (120 each), most used first
pnpm data:translate-ar merge <batch-file...>      # results shaped { fr, ar } (an array or { entries }) -> the dictionary, as draft
pnpm data:translate-ar check                      # quality guards on the dictionary; exit 1 on errors
pnpm data:translate-ar apply [--dry-run] [--only-reviewed]   # add ar to the YAML
pnpm data:translate-ar review [--out <md>]        # review sheet -> data-staging/translations/AR-REVIEW.md
pnpm data:translate-ar mark-reviewed [--all | --fr-file <file>]   # one French text per line
```

Workflow: `export`, translate the batch files in parallel (each result is a JSON array of `{ fr, ar }`), `merge` them (a different `ar` for a text already in the dictionary is a conflict and is refused; a text that is not in the current todo is skipped with a warning), `check`, `apply`, `review`, the owner corrects the dictionary and runs `mark-reviewed`, then `apply` again. All commands take `--data-dir` (default `data`) and `--dictionary` (default the committed file).

- `apply` adds `ar: { text, status }` right after `en` (after `fr` when there is no `en`) in the layout of the neighbouring block, for every node whose `fr.text` equals an entry exactly. It never changes an existing `ar` text and touches no other line. Its one other edit: a `draft` `ar` node whose text equals a `reviewed` entry's `ar` becomes `reviewed`. Every edited file is re-parsed and compared with the expected data before anything is written, and the run refuses a dictionary that fails `check`. `--only-reviewed` ignores draft entries; `--dry-run` writes nothing and prints counts per collection. It prints nodes filled, nodes upgraded, entries used and unused, and nodes still missing.
- `check` rules: (a) `ar` has Arabic letters; (b) every run of digits in `fr` appears as Latin digits in `ar`, and no Arabic-Indic digit appears; (c) every ALL-CAPS acronym of 2+ letters and every URL of `fr` appears unchanged in `ar`; (d) `ar` differs from `fr`; (f) the same `{` and `}` as `fr`; (g) more than 40% Latin letters is an error, 25 to 40% a warning; (h) no leading or trailing whitespace and at most 400 characters (the data schema limit).
