## Review focus

- **Two devices, same item, opposite operations** (phone unsaves X while laptop saves X): the last operation to reach the server wins for that item only, every other item is untouched, and both devices converge on next hydration. Test in todo 13 (per-item idempotency) and todo 14 (hydration convergence).
- **Profile edited on two devices:** the second save gets `conflict` with the server's current profile; the form keeps the student's values and offers "use the other version" / "keep mine". Test: todo 13 (CAS returns conflict, row unchanged), todo 14 (store surfaces conflict without rollback of the form), race version in `tests/db-race/` (2b).
- **Privacy notice changes after sign-up:** a user whose `consentVersion` is older than `CURRENT_CONSENT_VERSION` is sent back through the finish-signup gate and every account action returns `consent_required`. Test: todo 10 (gate) and todo 13 (actions refuse).
- **Stale pending signup:** a `pending_signups` row created under an older consent version (or expired) is treated as no consent at create time. Test: todo 9 (`evaluateAdmission` with a stale version), todo 10 (expired row).
- **Saving the 12th programme from two devices at once:** exactly one succeeds, the other gets `saved_limit` and rolls back with a notice. Test: `tests/db-race/saved-cap.test.ts` (2b harness, written in todo 13).

## TL;DR (For humans)
<!-- Fill this LAST, after the detailed plan below is written, so it summarizes the REAL plan. -->
<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**Who this is for and what changes for them:** A student can now make a Jisr account with Google or a one-time email link, after ticking a consent box and confirming they are 16 or older. Their saved universities, profile and application checklist follow them from phone to laptop, they can report an outdated fact in place, and they can download everything we hold or delete their account entirely. Without an account, nothing changes: the app works exactly as it does today.

**What you'll get:** Working accounts on top of the existing app — sign-in and consent, a database for user data only (never the university data), a one-time import of whatever a student had saved as a guest, an account page with "download my data" and "delete my account", updated privacy and terms pages in all three languages, and an official record of the decisions made along the way.

**Why this approach:** Two choices carry the plan. When a student is signed in, the database is the single source of truth — saves update instantly on screen and sync in the background, and if a save fails it visibly reverts instead of silently losing data. And account creation stays mechanically disabled until the Moroccan data-protection declaration is filed: one switch, off by default, so merging this work can never accidentally launch accounts early.

**What it will NOT do:** No passwords or extra sign-in methods, no admin dashboard, no university data in the database, and no changes at all for visitors who don't sign in. The declaration filing and provider account setup remain yours to do.

**Effort:** XL
**Risk:** Medium - this is a new subsystem touching shared stores, but the switch-off default, unmodified guest tests, and per-step rollback semantics contain the blast radius.
**Decisions to sanity-check:** database-authoritative sync (chosen over a local-first mirror); the email provider is Brevo (EU); the report button appears on every real fact in the student's journey but not on demo/marketing surfaces; one environment switch gates all account creation.

## PR 2 execution notes (2026-10-15)

Durable decisions from executing todos 10, 11, 13-17 (branch `feat/accounts-phase-2-part2`); PR 3 todos must honour them, and todo 23 copies the relevant ones into ADR 0013.

- **Routes:** the sign-in/sign-up surface is `/[locale]/sign-in?return=…`; every redirect-based sign-in lands on `/[locale]/welcome?return=…`. One zod-free builder (`src/lib/auth/callback-urls.ts`: `authCallbackUrls`, `safeReturnPath`, `signInPath`, `finishSetupPath`) makes every callback URL; a contract test pins the call sites. Return paths allow only plain segments under a known locale.
- **Kill switch on static pages:** server components read `accountsEnabled()` at prerender (deploy time on Vercel); with the flag off the sign-in and welcome pages are `notFound()` and every account entry renders nothing, so guest markup is unchanged. The per-request gates stay in the auth handler, the signup action and every account action.
- **Sign-up:** "signup" mode writes the `pending_signups` row (15 min, `CURRENT_CONSENT_VERSION` verbatim) before the link is sent; "signin" mode writes none, and an unknown address comes back as `AGE_NOT_CONFIRMED`, shown as "no account yet". The magic-link cooldown is claimed once, in a Better Auth `hooks.before` for `/sign-in/magic-link`, before the verification row exists (covers the action and a direct POST). The finish-signup gate asks for consent only: a user row cannot exist without age evidence.
- **Local storage:** guest keys (`jisr.profile`, `jisr.saved`, `jisr.plan`, `jisr.profile-draft`) hold only unclaimed guest data. The signed-in cache lives only under `jisr.account.` (draft included) plus the `jisr.auth` hint. Sign-out removes `jisr.auth` and `jisr.account.*` only; a fresh sign-in clears `jisr.account.*` before setting the hint. Clear my data keeps `jisr.auth` and removes every other `jisr.` key (signed-out behaviour unchanged). Todo 21 must list the `jisr.account.*` family.
- **Actions:** every account action runs `requireAccountReady()` inside `guarded()` (logs only the action name and SQLSTATE; Drizzle errors carry parameters) before Zod parsing; bounds are tighter than the columns and live in the zod-free `src/lib/constants.ts`. Caps (12 saved, 50 plan programmes, 20 feedback reports per rolling 24 h) run under `SELECT … FOR UPDATE` on the user row.
- **Profile revisions are monotonic per user:** `user_data_state.profile_revision` (migration 0001) keeps the highest revision of a deleted profile, and every new profile row starts above it under the user lock, so a stale device always gets `conflict`.
