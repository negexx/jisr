# Data wave 3 — the `coverage: complete` pilot

**Date:** 2026-10-17/18 · **Branch:** `data/w3-complete-pilot` · **Base:** `origin/main` `f0cc00ef`
**Scope:** FR / DE / NL / HU · **Sample:** 27 programmes · **Record edits:** 1 complete, 26 partial
**Review sheet (read this before merge):** `docs/reports/2026-10-18-data-wave-3-review.md`

This wave answers one question the data-correctness audit raised (`P0-1`): can a programme's
`requirements.coverage` be set to `complete` — i.e. can the requirement set an official page states
for an international (non-EU) applicant be **fully captured** by the rule kinds the match engine
evaluates? The audit found **0 of 1242** programmes were `complete`. This pilot sampled 27 and
produced **1** that qualifies.

---

## 1. Selection rule (reproducible)

From `data/programs/*.yaml`, in this order:

1. **Country** ∈ {FR, DE, NL, HU}.
2. **English-taught** (`teachingLanguages.value` contains `en`) — the Release-1 audience is served
   English-taught first, and an English requirement is the rule we can most often capture.
3. **An institution-hosted source** — at least one `sources.*.url` whose host is *not* a pure
   listing/register service (`daad.de`, `parcoursup`, `tempus.tpf.hu`/Study Finder). This is the
   operational form of "the official page set includes a clear requirements/admissions page".
4. **Sort by slug ascending**, then take a deterministic systematic sample per country:
   `index(k) = floor((k + 0.5) · N / K)` for `k = 0 … K−1`, skipping repeats.
5. **Quotas** (≈ proportionate, English-taught pool sizes in brackets):
   FR 6 (pool 16), DE 8 (pool 127), NL 5 (pool 5), HU 8 (pool 111) → **27**.

Script: `node /tmp/opencode/w3/select.cjs` (the deterministic rule above; not committed). The 27
slugs are listed in `data-staging/w3/slugs.txt` (untracked). NL's English-taught pool is tiny (5
records; the two Hall Larenstein campuses are distinct slugs), so all 5 were taken.

## 2. Method

1. **`pnpm data:pages --slugs … --search --topics --max-queries 300`** — built the reader's pages
   file. Result: **82 SERPER queries**; FR 6 programmes (2 skipped, no institution website), DE 8,
   NL 5, HU 8; programme / fee / admission pages found for most. Output:
   `data-staging/w3/pages.json` (untracked).
2. **`pnpm data:read --model deepseek-v4.1-flash --pages … --slugs … --max-usd 4`** — **failed**:
   all 27 calls returned `HTTP 401 api_key_expired` (`OPENCODE_API_KEY` in `.env.local` is expired).
   **0 facts proposed, $0.00 spent.** Because the task requires reading the requirements page
   anyway, the reading was done manually instead (next step); no proposal was used as a fact.
3. **Manual read of the requirements/admissions page** of every sampled programme (the programme's
   own page plus, where present, a dedicated admissions page and the DAAD/Study-Finder register
   page for cross-checking). Verbatim quotes were captured from the fetched page text
   (`curl` + a tag-stripping helper; the helper and the saved pages live under `/tmp/opencode/w3/`,
   untracked).
4. **Decision** per programme (see §4) and **direct record edit** where `complete` was justified.
5. **`pnpm data:check`** and **`pnpm exec vitest run tests/data-schema tests/domain tests/lib`**.

---

## 3. Decision settled — what `complete` means here

**Settled:** a programme may be `requirements.coverage: complete` only when **every requirement its
official admissions page states for an international/non-EU applicant is captured by a structured,
evaluable rule** (`language_proficiency`, `subject_taken`, `prior_study_years_min`,
`credential_type_in`, `credential_track_in`, `overall_grade_min`, `subject_grade_min`), each with a
verbatim quote from an official page. The **admission route** represents the general
credential/entrance-qualification requirement and the **application channel** represents the
application platform (e.g. uni-assist VPD); a requirement already represented there is **not**
duplicated as a programme rule. Any of the following forces `partial`:

- an **entrance examination / interview / portfolio / aptitude test** (a non-evaluable step);
- an **NC / ranking / points threshold** without a published threshold ("unpublished");
- a **credential-assessment step not expressible as a rule** (HZB/ASK assessment, Dutch-diploma
  equivalence, colloquium doctum);
- a **numeric-only test score with no CEFR level** (e.g. "TOEFL ibt 83, or equivalent") — the rule
  vocabulary stores a CEFR level and test names, not scores;
- a **vague or soft** statement ("proof may be required", "recommended", "a good command").

**Alternative rejected:** treating `manual_check` as an acceptable rule for these blockers (so
"complete" would mean "the set is listed, even if a human must evaluate it"). That reading would
mark most sampled programmes `complete` while the match still returns ⚠️ and while `data:check`
prints a `complete` + `manual_check` warning — it would make `complete` an empty claim and put the
"we captured every requirement" badge next to an unevaluated exam. The task's "prefer partial
whenever uncertain" and the trust promise both point the other way.

**Consequence:** `complete` is reachable, but only for the narrow case where a programme's
*programme-specific* requirements are all structured. In this sample that is exactly one programme.

### Top reason, aggregated

**Every non-complete programme fails on a requirement that is not expressible by the current rule
kinds.** The two dominant classes:

1. **A selection step the engine cannot evaluate** (entrance exam, interview, aptitude test, NC
   ranking) — 17 of the 26.
2. **A credential/equivalence step not representable as a rule** (HZB/ASK assessment, Dutch-diploma
   equivalence, 21+ colloquium doctum, VPD when not a channel) — the rest; plus one page blocked
   (HTTP 403) and two FR records whose extra `manual_check` is a tuition note, not a requirement.

## 5. Findings the owner should act on

1. **`complete` is structurally rare, not merely unattempted.** For these four destinations the
   international admission decision almost always turns on an entrance exam, an NC ranking, or a
   credential assessment. To scale `complete`, the schema would need new rule kinds (e.g. an
   `entrance_exam`/`selection` kind, or a `credential_assessment` representation) — a code+ADR
   change, not a data change. Without it, the honest ceiling is "language/subject-only programmes".
2. **The demo's coverage override is more than illustrative.** `scripts/data/demo-fixture.ts` flips
   `coverage` to `complete` on three real programmes to show a satisfied match. This pilot shows the
   flag is justified for at most one of the 27 sampled programmes, so the demo's "complete" remains
   an explicit illustration, not a pattern that scales.
3. **A misplaced requirement rule.** Several FR records carry a `manual_check` whose text is a
   **tuition** note ("Droits d'inscription différenciés…"), not an admission requirement. It keeps
   their coverage `partial` for a non-requirement reason. Worth a separate cleanup pass (out of
   scope here).
4. **One page blocked the reading.** BUas (`nl-breda…`) returns HTTP 403 to the project
   User-Agent; its requirement set could not be verified.
5. **`OPENCODE_API_KEY` is expired.** `data:read` (and every model-backed script) cannot run until
   it is renewed. This wave did not depend on it (the page must be read by a human anyway), but
   W4+ will.

## 8. Assumptions

- "Today" for `data:check` is **UTC 2026-10-17** (the machine clock reads 2026-10-18 local, which
  `data:check` rejects as a future date), so the one new source is stamped `2026-10-17`.
- The NL English-taught pool is only 5 records; all were taken, so NL's stratum is a census, not a
  sample.
- "Institution-hosted source" excludes `daad.de`, `parcoursup` and `tempus.tpf.hu` (Study Finder),
  which are registers/listings, not the institution's own requirements page.
