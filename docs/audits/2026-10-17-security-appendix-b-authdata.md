## Candidates

### C1 — Consent/age evidence is client-asserted: a crafted sign-in request stamps `consent_version`/`consented_at` for a privacy notice that was never shown

- **File/function:** `src/lib/auth/server.ts:76-91` (`admissionEvidence`), `src/lib/auth/admission.ts:64-69` (`confirmationFromOAuthState`), `src/components/auth/sign-in-form.tsx:122-136` (the Google button's `additionalData`), `src/lib/server/signup.ts:121-124` + `src/lib/auth/pending-signup.ts:20-31` (the magic-link twin), reached from `src/lib/auth/server.ts:328-353` (`databaseHooks.user.create.before`).
- **Attacker capability:** any anonymous visitor, for **their own** identity only. Google proves the mailbox (`server.ts:84` requires `user.emailVerified === true`), and the magic-link path needs the emailed token, so nobody can do this to a third party's address.
- **Attack path (Google):** `POST /api/auth/sign-in/social` with `{"provider":"google","additionalData":{"ageConfirmed":true,"consentVersion":"<CURRENT_CONSENT_VERSION>"}}` → `generateState` spreads `additionalData` into the OAuth state (`node_modules/better-auth/dist/oauth2/state.mjs:23-34`) → the callback's `parseState` puts it in the ALS state (`state.mjs:63`) → `confirmationFromOAuthState` reads the top-level booleans (`admission.ts:64-69`) → `evaluateAdmission` stamps `{consentVersion: currentVersion, consentedAt: now}` (`admission.ts:49-52`) onto the created user. The browser never rendered the sign-in form, never displayed the privacy notice and never ticked a box. The state is encrypted and cookie-bound (`state.mjs:57-91,92-150`), so this is *not* a third-party injection — it is a self-declared record. **Magic-link twin:** the Server Action accepts `consent: true, ageConfirmed: true` as plain booleans (`signup.ts:121-124`) and `recordPendingSignup` then hardcodes `ageConfirmed: true` + `consentVersion: CURRENT_CONSENT_VERSION` (`pending-signup.ts:21-26`); a scripted action call is indistinguishable from the form.
- **Impact:** **Low (record integrity / audit value, self-inflicted).** The DB can hold a consent record asserting an act that never happened, and the age floor is unenforceable beyond self-declaration. It is not an account takeover, not third-party data access, and not a bypass of the *server-side* gate in the sense of missing evidence — the evidence itself is the client's word. This matters only if the `consent_version`/`consented_at` row is treated as legal proof of consent (CNDP). If it is treated as "the student asserted it at sign-in", the design is fine and this is informational.
- **CWE candidate:** CWE-807 (Reliance on Untrusted Inputs in a Security Decision); CWE-602 (Client-Side Enforcement of Server-Side Security) as the weaker framing.
- **Evidence (quoted):**
  - `sign-in-form.tsx:127-131` — `authClient.signIn.social({ provider: "google", ...authCallbackUrls(...), additionalData: { ageConfirmed: true, consentVersion: CURRENT_CONSENT_VERSION } })` — the only thing that enforces the checkboxes is `block(confirmationErrors())` above it, client-side.
  - `admission.ts:64-69` — `ageConfirmed: state.ageConfirmed === true, consentVersion: typeof state.consentVersion === "string" ? state.consentVersion : null` — top-level keys of the state, which `oauth2/state.mjs:24` fills from `options?.additionalData`.
  - `server.ts:84` — `if (user.emailVerified !== true) throw googleEmailNotVerifiedError();` — the one real server check on this path.
  - `pending-signup.ts:22-25` — `consentVersion: CURRENT_CONSENT_VERSION, consentedAt: now, ageConfirmed: true` — server-written values sourced from the action's client booleans.
- **Safe verification idea:** local PGlite harness (`scripts/db/harness.ts`; the `tests/lib/auth/google.test.ts` callback-driving pattern). Drive `POST /api/auth/sign-in/social` with the crafted `additionalData` and a mocked Google token exchange, then assert the created `user` row has `consent_version = CURRENT_CONSENT_VERSION` and a non-null `consented_at` while no form/page was rendered. Also drive `requestSignInLink` with `consent:true, ageConfirmed:true` and assert the pending row's values. Reserved `@example.org` addresses only; no network, no production.

### C2 — No rate limiting anywhere: unauthenticated `POST /api/auth/sign-in/social` writes unbounded `verification` rows, and `POST /api/auth/magic-link/confirm` does unbounded DB work

- **File/function:** `src/lib/auth/server.ts:267` (`advanced: { ipAddress: { disableIpTracking: true }, ... }`) → `node_modules/better-auth/dist/api/rate-limiter/index.mjs:242-243`; the writing endpoint `node_modules/better-auth/dist/api/routes/sign-in.mjs:118-240` (`signInSocial`, no `use:` middleware, no session) → `oauth2/state.mjs:17-45` → `state.mjs:57-91` (`generateGenericState` → `createVerificationValue`, `auth-state:<32 random>`); the reading endpoint `src/lib/auth/magic-link-confirm.ts:54-109`; the app's only purge `src/lib/server/email-cooldown.ts:71-85` (does not touch `verification`).
- **Attacker capability:** unauthenticated HTTP client (curl/script). No cookie, no session, no CSRF barrier for this shape (see below), no rate limit.
- **Attack path:**
  1. **Write amplification (the new part):** every `POST /api/auth/sign-in/social {"provider":"google"}` creates one `verification` row (`identifier = "auth-state:<32 random>"`, value ≈ 350–400 bytes of JSON: `callbackURL`, 128-char `codeVerifier`, `expiresAt`, `oauthState`, `additionalData`) and returns `200` with the authorize URL. The row is deleted only if the matching callback is ever completed (`state.mjs:142`); the app's lazy purge deletes `pending_signups`/`email_cooldowns`/`auth_email_days` only (`email-cooldown.ts:74-81`), and account erasure sweeps only rows naming a user (`account-erasure.ts:32-39`). An abandoned attacker-driven flow therefore leaves a row **forever**. Rows are bounded only by the platform (Neon Free 1 GB storage, ADR 0013 "Facts checked"); ~2M rows fill it, and Vercel function invocations are consumed on the way.
  2. **Read amplification:** `POST /api/auth/magic-link/confirm` with random 32-char tokens is unlimited; each request runs `consumeVerificationValue(nonceIdentifier(token))` (transaction + `findMany` + delete, `internal-adapter.mjs:815-858`) and then the plugin's verify (`findVerificationValue`), i.e. ~2–3 indexed statements per junk request, with no auth and no cap. Token entropy (62³²) makes guessing infeasible, so this is availability/cost, not compromise.
- **Why no limiter fires:** `getIP` returns `null` by design when `disableIpTracking` is set (`@better-auth/core/dist/utils/ip.mjs:203-204`), and `resolveRateLimitConfig` then returns `null`, switching the limiter off globally (`rate-limiter/index.mjs:243`). The project knew the email consequence (ADR 0013 §9) and built `email_cooldowns` + `AUTH_EMAILS_PER_DAY` for **sends**, but those cover only `/sign-in/magic-link`; they do not cover `/sign-in/social` or `/magic-link/confirm`. Media type is no barrier: the router allows only `application/json` (`api/index.mjs:163`), which any HTTP client sends; no browser is needed, so CORS/CSRF are irrelevant here.
- **Impact:** **Low** (availability/operational; no data read or write on a victim's behalf). Self-limiting in the sense that Vercel Hobby caps and Neon Free limits auto-pause the site rather than bill — which is itself the harm (site down, storage growth). A sustained flood could reach Medium operationally, but nothing is exfiltrated and no account is affected.
- **CWE candidate:** CWE-770 (Allocation of Resources Without Limits or Throttling); CWE-799 (Improper Control of Interaction Frequency) for the confirm endpoint.
- **Evidence (quoted):**
  - `sign-in.mjs:118-121` — `const signInSocial = () => createAuthEndpoint("/sign-in/social", { method: "POST", operationId: "socialSignIn", body: socialSignInBodySchema, metadata: {...} }, async (c) => {` — **no `use:` array**, unlike `signInEmail` (`sign-in.mjs:244`: `use: [formCsrfMiddleware]`).
  - `sign-in.mjs:222-225` — `const { codeVerifier, state } = await generateState(c, { additionalData: c.body.additionalData, idTokenNonce });` → state row written before any URL is returned.
  - `state.mjs:79-86` — `await c.context.internalAdapter.createVerificationValue({ value: JSON.stringify({...stateData, oauthState: state}), identifier: getAuthStateVerificationIdentifier(state), expiresAt })` with `expiresAt` = +10 min and **no scheduled deletion**.
  - `rate-limiter/index.mjs:242-243` — `const ip = getIP(req, ctx.options); if (!ip && ctx.options.advanced?.ipAddress?.disableIpTracking) return null;` + `ip.mjs:203-204` — `if (options.advanced?.ipAddress?.disableIpTracking) return null;`.
  - `email-cooldown.ts:74-81` — the purge deletes only `pending_signups`, `email_cooldowns`, `auth_email_days`; `verification` is absent.
  - `server.ts:361-370` — the `verification.create.before` hook only refuses while accounts are off, so the vector exists exactly while accounts are live (the production state per the brief).
- **Safe verification idea:** local PGlite harness (the `tests/db/magic-link-confirm.test.ts` pattern: `startTestDatabase`, `ACCOUNTS_ENABLED=true`, `BETTER_AUTH_SECRET/URL`, import `@/app/api/auth/[...all]/route`). (i) Send N=50 unauthenticated `POST /api/auth/sign-in/social` requests with `{"provider":"google"}`; assert every response is 200 and `select count(*) from verification where identifier like 'auth-state:%'` grew by N. (ii) Then call any granted auth-email path (or `claimAuthEmailSend`) and assert the state rows still exist (purge does not cover them). (iii) Send N junk-token `POST /api/auth/magic-link/confirm` requests; assert all 400 and count pool queries via a counting wrapper to show ~2–3 statements each with no 429. Reserved addresses only; all local.

## Checked and sound (with evidence)

Items 1–20 of `docs/audits/drafts/t2-hunter-surface.md` already list many shared checks; below are the checks **specific to this brief** that I verified myself, plus the ones I independently confirmed with evidence. Where the surface draft already lists an item, it is marked "also in surface".

1. **Every Server Action and route handler that touches user data re-checks the session server-side — no counterexample found.** `account-actions.ts` (all 9 exports) goes through `withReadyAccount`/`guarded(requireAccountReady)` (`account-actions.ts:41-107`, `account-guard.ts:26-37`); `importGuestData` (`import.ts:19-28`); `acceptCurrentConsent` (`server.ts:21-31` of `lib/server/consent.ts`); the export route (`account-export.ts:27-43`); `requestSignInLink` is intentionally public and reads no session (`signup.ts:113-143`). `readSessionUser` re-reads from the DB on every call (no cookie cache configured, `session.ts:15-22`). The only two route handlers in `src/app/api` are the Better Auth catch-all and the export. *(also in surface)*
2. **No IDOR: every operation is keyed by the session user id, never by client input.** No action or store function accepts a `userId`; inputs are `strictObject`s without identity fields (`account-inputs.ts:34-109`), and all `where` clauses use `ready.userId` (`account-store.ts:165,184,187,205,214,235,264,293,329-336`; `import-store.ts:104-133`; `consent.ts:29`). The export selects by `sessionUser.id` (`account-export-store.ts:104,110,118,129,137,149,156`) and has a test that another student's rows are not mixed in (`tests/app/api/export.test.ts:452-492`). *(also in surface)*
3. **Session cookie and lifetime are the secure defaults.** `__Secure-` prefix when the base URL is https, `secure: true`, `sameSite: "lax"`, `httpOnly: true`, `maxAge` = 7 days (`node_modules/better-auth/dist/cookies/index.mjs:23,32-37,49`); `expiresIn` 7d, `updateAge` 24h, `freshAge` 24h (`context/create-context.mjs:146-149`). No cookie cache is configured, so authorization always re-reads the DB. Session fixation: every sign-in creates a new server-side session (`internal-adapter.mjs:308` `createSession`), and no pre-auth session is elevated.
4. **Sign-out revokes server-side, not just client-side.** `POST /sign-out` reads the cookie, deletes the session row by token and then clears the cookie (`api/routes/sign-out.mjs:42-54`). Client-side, `AccountMenu.signOut` clears the hint and the account cache only after the server answered without error (`account-menu.tsx:65-83`).
5. **Sign-out CSRF (hunt item 7) is not exploitable — checked, not assumed.** The router accepts only `application/json` (`api/index.mjs:163`; enforcement in `better-call/dist/router.mjs:60-67` + `utils.mjs:8-22`), and an HTML form can only send `application/x-www-form-urlencoded`/`multipart`/`text/plain`, so a cross-site form POST gets `415` before the handler; a cross-site `fetch` with JSON triggers CORS preflight and is refused. The global origin check additionally refuses any cookie-bearing request from a foreign origin (`origin-check.mjs:96-118`), and `SameSite=Lax` keeps the cookie off cross-site POSTs anyway. Same reasoning closes cross-site CSRF on `POST /delete-user` and every other auth POST.
6. **The magic-link confirm endpoint is CSRF-protected for the cookie-less case too.** `magic-link-confirm.ts:66` `use: [formCsrfMiddleware]`; the middleware blocks `Sec-Fetch-Site: cross-site` navigations and, for any browser-marked request, forces an Origin/Referer trusted-origin check even without cookies (`origin-check.mjs:131-153`). Tests drive the cross-site cases (`tests/db/magic-link-confirm.test.ts:278-300`). *(also in surface)*
7. **Magic-link tokens: 15-minute expiry, hashed at rest, single-use, and expiry is enforced by the atomic consume.** `expiresIn: MAGIC_LINK_EXPIRY_S` (15 min) and `storeToken: "hashed"` (`server.ts:43,226-228`); the plugin consumes via `consumeVerificationValue` before doing anything else (`plugins/magic-link/index.mjs:170-176`), and the adapter deletes every row for the identifier and treats `expiresAt < now` as invalid (`internal-adapter.mjs:787-858`, esp. `:843-846,856`). Replay tests exist (`magic-link-confirm.test.ts:269-276`).
8. **Mail scanners / prefetchers cannot sign in or delete: both emailed links land on inert pages and act only on a button.** The GET `/magic-link/verify` and GET `/delete-user/callback` are closed with `NOT_FOUND` by the before hook (`server.ts:147-150`); the emailed URLs carry the token in the fragment and empty query (`callback-urls.ts:134-142,104-106`), which no request line, log or Referer carries; the confirm islands strip the fragment immediately (`sign-in-confirm.tsx:53-59`, `account-delete-confirm.tsx:35-43`). Tests: `magic-link-confirm.test.ts:134-172`, `tests/lib/auth/delete-account.test.ts:437-444`. *(also in surface)*
9. **The soft nonce is implemented correctly for what it claims to be.** 24 random bytes, only `sha256(nonce)` stored, keyed to `sha256(token)`, `timingSafeEqual` with a length pre-check, HttpOnly/Lax/`/api/auth`-scoped cookie, `Secure` when the base URL is https (`magic-link-nonce.ts:30-50,52-69`); the nonce row expires with the link and is consumed before the token. A missing/mismatched nonce still signs in (cross-device is deliberate) but only withholds the guest import (`magic-link-confirm.ts:80-104`, `post-auth-landing.tsx:193-197`). *(also in surface)*
10. **Consent/age cannot be omitted: every create path without evidence is rejected.** `evaluateAdmission` rejects unless `evidence.ageConfirmed === true` and never stamps a non-current version (`admission.ts:43-53`); evidence is path-scoped and never combined (`server.ts:76-91`); a direct `POST /sign-in/magic-link` writes no pending row because the ALS intent can only be set by the Server Action after its consent check (`signup-intent.ts:16-21`, `server.ts:151-158`), which the test suite proves end-to-end (`magic-link-confirm.test.ts:219-233`; `tests/db/admission.test.ts:163-172`). The crafted-request residual is C1 above. *(partly also in surface)*
11. **Stale consent versions fail closed.** `hasCurrentConsent` is exact-match (`consent.ts:6-8`); a stale/absent version yields NULL consent at create (`admission.ts:49-51`) and every account action answers `consent_required` via `requireAccountReady` (`session.ts:26-31`); `acceptCurrentConsent` stamps the constant and the server clock on the session's own row only (`lib/server/consent.ts:21-31`).
12. **`pending_signups` / `email_cooldowns` throttling and caps are atomic and cannot be raced.** One `INSERT … ON CONFLICT DO UPDATE … setWhere` per claim (`email-cooldown.ts:22-37,46-61`), cooldown before budget so a refused mailbox request spends nothing (`:107-115`), deletion reserve honoured by a kind-specific limit (`:97-101`), both races covered by `tests/db-race/email-cooldown.test.ts` / `email-daily-cap.test.ts`. The refused-resend `consented_at` refresh was F2 and is fixed: the row is written **after** the claim (`server.ts:151-158`). *(also in surface; ADR §3 doc drift noted there)*
13. **Erasure covers `email_cooldowns` explicitly, in both key forms.** `account-erasure.ts:41-43` — `delete(emailCooldowns).where(inArray(emailCooldowns.email, [email, cooldownKey(email)]))` — the mailbox key (`+tag`/Gmail-dot normalised) and the raw address, all kinds. `pending_signups` by normalised email (`:44`), verification rows by user id / magic-link email / OAuth-link user or email (`:32-39`, JSON-safe via `pg_input_is_valid`). The one deliberate omission — the Q19 nonce row (`magic-link-nonce:<hash>`, names no user, 15-min expiry) — is documented at `:24-26` and is correct: the `LIKE 'magic-link:%'` pattern does not match `magic-link-nonce:` (11th char `-` vs `:`), and the value is not JSON. *(also in surface)*
14. **Deletion is a session-bound, single-use, one-hour credential; cross-user and replay paths fail.** `DELETE_TOKEN_EXPIRY_S = 3600` (`server.ts:44,293`); the POST runs behind `sensitiveSessionMiddleware` (`update-user.mjs:219-222,282-296`), and the callback checks `token.value !== session.user.id` → `INVALID_TOKEN` (`update-user.mjs:373-376`). Tests: garbage token, expired token, **another student's token**, no session (`tests/lib/auth/delete-account.test.ts:381-444`). The GET callback never deletes (`:437-444`). The session cookie is expired on the real response by the after hook (`server.ts:164-168`), which is needed because the inner plain call drops its `Set-Cookie`.
15. **The export endpoint has no exploitable CSRF: it is a read-only GET and the response is unreadable cross-origin.** `GET /api/account/export` requires a session (401) and current consent is deliberately not required (`account-export.ts:27-43`); `Cache-Control: no-store` + `Content-Disposition: attachment` (`:13,38-41`); a cross-site navigation can at most trigger a download the attacker cannot read (SOP, no CORS headers, and `frame-ancestors 'none'` blocks framing — `security-headers.ts:7`). Column allow-list excludes sessions, verification, OAuth tokens, password, IP/UA (`account-export-store.ts:20-24,85-232`), with tests for secrets and ownership (`tests/app/api/export.test.ts:518-563`).
16. **Open redirect / return-path handling is closed in both directions.** `safeReturnPath` requires a leading `/`, a known locale as the first segment and `[A-Za-z0-9._~-]` segments that are not `.`/`..`, so `//evil.com`, `/\evil`, `%2F`-escapes, `javascript:` and query/fragment injections all fall back to the locale home (`callback-urls.ts:16-31`); it is applied at every read/write site (`:45-48,72-76,134-142,153-161`), and the magic-link URL's `return` is re-derived from the plugin URL and re-validated (`server.ts:204-222`). The landing's `error` is a regex-bounded code rendered as static copy (`callback-urls.ts:108-119`). *(also in surface)*
17. **No email template/header injection.** Templates are static strings with no user-controlled interpolation except the server-built link and privacy URL (`email.ts:100-213`); the address is validated before any claim (`server.ts:153-154`, `email-shape.ts:7-12`) and the Brevo call is a JSON API with a fixed subject and `textContent` only (`email.ts:281-294`). The emailed link is built from the env-pinned `BETTER_AUTH_URL`, never from a request `Host` (`server.ts:390-405`), so host-header poisoning cannot alter it. *(also in surface, partly)*
18. **Postgres/Drizzle: parameterised SQL, no raw user input, CAS and lock boundaries hold.** The only `sql.raw` calls use compile-time constant lists (`schema/app.ts:38,113`); every other fragment is a tagged template (parameters) including the erasure JSON logic (`account-erasure.ts:18`) and the cooldown/counter claims (`email-cooldown.ts:29-33,56-57`). `saveProfileFor` is a true compare-and-set with a monotonic revision floor and a locked first insert (`account-store.ts:255-285`), with race specs (`tests/db-race/profile-cas.test.ts`, `profile-revision.test.ts`); caps/import/clear/feedback serialise on `lockUser` `FOR UPDATE` (`account-store.ts:82-89`).
19. **Kill switch: no bypass found.** `accountsEnabled` is an allow-list read per call (`accounts-enabled.ts:8-14`); enforced in the route handler before Better Auth is constructed (`handler.ts:34-47`), the gate plugin (`accounts-gate.ts:41-50`), user/verification create hooks (`server.ts:333,367`), email send and claim (`server.ts:111-123`), `beforeDelete` (`server.ts:315`), `readSessionUser` so every action refuses (`session.ts:18`), the sign-up action's first line (`signup.ts:116`), `acceptCurrentConsent` (`lib/server/consent.ts:22`), the export route before any DB work (`account-export.ts:28`), the confirm endpoint (`magic-link-confirm.ts:72-77`), and the prerendered pages/entries (`sign-in/page.tsx:24,38`, `account-entry.tsx:11`, `account-sync-entry.tsx:12`). While off, `GET get-session` answers `200 null` and everything else `403` (`accounts-gate.ts:16-34`). *(also in surface)*
20. **Logs: no token/address/PII sink found.** `redactLogText` blanks URLs, `token=` values and addresses (incl. `%40`), objects are dropped, errors reduced to name+code (`log.ts:10-50`); `onAPIError.onError` wraps non-APIErrors into a detail-free 500 (`:58-66`); `guarded` logs action+SQLSTATE only (`account-guard.ts:14-21`); `failureOf` whitelists three variable-name-only classes (`signup.ts:62-111`). `tests/lib/privacy/no-pii.test.ts` drives the real flows and fails on any canary, including the nonce cookie value (`:340-357`).
21. **Personal-data minimisation holds.** Session `userAgent`/`ipAddress` are nulled by the create hook (`server.ts:325-327`), IP tracking is off (`server.ts:267`), Google `idToken` is nulled on create/update (`server.ts:357-360`), OAuth access/refresh tokens encrypted (`server.ts:274`), and the export omits them all. *(also in surface)*

## Open questions

1. **Is the consent record meant to be probative?** C1 means `consent_version`/`consented_at` prove "a request with these booleans arrived at time T", not "the notice was displayed and accepted". If the CNDP file relies on it as evidence of consent, the owner may want an explicit provenance note (or an "asserted by" semantic) rather than treating it as verified. Legal/product question, not a code defect.
2. **`beforeDelete` refuses while accounts are off (`server.ts:315`), and the account/delete pages are `notFound()` in the same state.** A student holding a valid deletion link (or wanting to delete) during a switch-off window cannot delete until accounts are switched on again. There is no offline erasure path (email/SQL runbook). GDPR availability question for the owner; no attacker path.
3. **Orphan `verification` rows are never swept** (C2): unused magic-link tokens and delete tokens (bounded by the daily cap) and, unbounded, attacker-driven OAuth state rows. If C2 is accepted as-is, the cheap fix candidates are a `verification` arm in `purgeExpiredAuthRows` (`expires_at < now()`) and/or a per-request cap on `/sign-in/social`; both are decisions, not audit findings.
4. **`email_cooldowns` erasure is by exact address + mailbox key; a verification row written for a *different alias* of the same mailbox** (e.g. `a+1@x.com` while the account is `a@x.com`) survives account deletion until it expires (≤15 min, no other data). Same for `pending_signups` (keyed by the normalised address only). Not exploitable; noted for completeness of the erasure story.
