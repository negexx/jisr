# ADR 0013 — Accounts (phase 2): optional sign-in, server-authoritative sync, rights and launch gates

**Status:** Accepted (refines ADR 0004 section 6 and ADR 0005 item 11). Accounts stay off in every environment (`ACCOUNTS_ENABLED` empty) until the owner clears the launch gates in decision 14.
**Date:** 2026-10-15

## Context

ADR 0003 (items 4 and 5) put user data, and only user data, in Postgres on Neon and made accounts (Better Auth, Google and magic link) an addition to a guest-first journey that imports the local profile once. ADR 0004 section 6 made the CNDP declaration, a privacy notice in en/fr/ar, unticked versioned consent and an age floor of 16 the gates for launching accounts, and promised JSON export and cascade deletion. ADR 0005 item 11 made a slug alias mechanism a prerequisite for accounts that persist slugs. Phase 2 was built in three pull requests from `docs/superpowers/plans/2026-10-14-accounts-phase-2.md` and `docs/superpowers/specs/2026-10-14-accounts-phase-2-design.md`. This ADR records what those documents and the code settled, including the points where reading the library or the code changed the plan. It refines ADR 0004 section 6 (deletion also erases the rows Better Auth leaves behind, and a session stores no IP address or user agent) and ADR 0005 item 11 (the alias mechanism now exists; the rule "do not rename a slug" stands until a rename is needed, decision 10).

Constraints behind every choice: one developer; free tiers only (Vercel Hobby, Neon, Brevo), so no worker, queue or cron (ADR 0003); a signed-out visitor gets today's journey with the same `jisr.*` keys, no new server call and no new prefetch; no profile value, email address or token reaches a log; and merging the code must never switch accounts on.

### Facts checked on 2026-10-15

Re-check each before relying on it at launch or after an upgrade.

- Brevo Free plan: up to 300 emails per day, once Brevo has approved the account for sending (https://www.brevo.com/pricing/).
- Neon Free plan: each project gets 100 CU-hours of compute per month, compute scales to zero when idle, and 1 GB of Postgres storage (https://neon.com/pricing).
- Next.js 16 (docs v16.2.9 through ctx7; installed 16.3.7): `redirect()` answers 307 and `permanentRedirect()` 308 outside a Server Action. A local fixture build prerenders the alias page as a real 307 with a `Location` header, not a meta refresh (`.next/server/app/fr/programs/xx-test-prog-old-ok.meta`).
- Better Auth 1.7.7, read in `node_modules/better-auth/dist`: `deleteUser` removes only the session, account and user rows, so verification rows survive (`db/internal-adapter.mjs`); an endpoint called as a plain function skips hooks (`api/dispatch.mjs`); a send run through `runInBackgroundOrAwait` that throws is logged and swallowed, so the caller still answers "sent" (`context/create-context.mjs`); a session lasts 7 days unless `session.expiresIn` is set, and the app does not set it; with IP tracking disabled Better Auth applies no rate limit, because its limiter keys on the client IP (`api/rate-limiter/index.mjs`).

## Decision

### 1. One kill switch, read on every request

- `ACCOUNTS_ENABLED` is an allow-list: only `true` or `1`, after trimming and lower-casing, turn accounts on (`src/lib/auth/accounts-enabled.ts`). Unset, blank, `false` and a typo leave them off. It is the legal launch gate (ADR 0004 section 6), so it fails closed.
- It is read per call, never frozen at build, in: the auth route handler (`src/lib/auth/handler.ts` answers on its own and never initialises Better Auth while off: `GET get-session` is a signed-out `200 null`, everything else `403 ACCOUNTS_DISABLED`), the `accountsGate` plugin, the user and verification create hooks, the email callbacks and `sendAuthEmail`, `beforeDelete`, the sign-in-link action (its first line, before any parsing or database work), `acceptCurrentConsent`, `readSessionUser` (so every account action answers `unauthenticated`) and the export route (`403` before any session or database work).
- Server components that render account surfaces read it at prerender, which on Vercel means at deploy time. With it off, the `sign-in`, `welcome`, `account` and `account/delete` pages are `notFound()` and every account entry (menu, sync loader, report slot) renders nothing, so the guest HTML is unchanged. Consequence: the owner sets the variable in the Vercel Production scope and then redeploys; switching it off again refuses every request at once, but already prerendered pages keep showing their sign-in surfaces until the next deploy.
- Nothing in the repository sets it: `.env.example`, CI, Vercel configuration and docs leave it empty, and tests set it per test. While it is on, a missing `BETTER_AUTH_SECRET`, or a missing or non-http(s) `BETTER_AUTH_URL`, answers `500 AUTH_MISCONFIGURED`. The base URL is never inferred from a request, so a forged `Host` header cannot poison magic-link or deletion URLs.

### 2. Admission, consent and age

- The gate is `databaseHooks.user.create.before` in `src/lib/auth/server.ts`; the decision is the pure `evaluateAdmission` in `src/lib/auth/admission.ts`. Evidence is scoped to the path that creates the user and is never combined: `/callback/:id` reads the OAuth state only (and refuses a Google address Google has not verified), `/magic-link/confirm` reads the `pending_signups` row only (Better Auth's GET `/magic-link/verify` is closed, decision 4), and any other path (Google ID-token sign-in, server calls) has no evidence and is rejected. Age not confirmed: rejected with `AGE_NOT_CONFIRMED`, no user row exists. Age confirmed but consent absent, or given for any version other than the current one: the user is created with null consent fields and the finish-signup gate holds every account feature until the student consents.
- `validateUserInfo` is not the gate. It runs before the create hook, and `input: false` keeps consent fields out of user input, so a consent check there could not be satisfied.
- Age is a confirmation, never a birthdate; under-16 visitors stay guests. Consent is an unticked checkbox, and the server stamps `consented_at` with its own clock.
- Consent is versioned. `CURRENT_CONSENT_VERSION` (`src/lib/auth/consent.ts`, zod-free so client and server share it) equals the `consentVersion` in the frontmatter of `content/{fr,en,ar}/privacy.mdx`; `tests/app/legal-pages.test.tsx` ties them, and any change to the notice bumps both in one commit (pre-release exception, 2026-10-16: while accounts are unreleased, a notice edit for an unshipped feature — the ruling Q19 sign-in-cookie line — ships without a bump; the first launch bump covers it, and P23 re-prompts at sign-in). `requireAccountReady()` (`src/lib/server/session.ts`) checks `consentVersion === CURRENT_CONSENT_VERSION`, so after a notice change every account action answers `consent_required` and the browser offers "finish setting up" (account menu, sync notices, clear dialog) until `acceptCurrentConsent` stamps the new version. That stamp is a direct update of the session's own user row, because `updateUser` refuses `input: false` fields.
- Sign-up writes the `pending_signups` row before the link is sent (keyed by normalised address, `CURRENT_CONSENT_VERSION` verbatim, server-clock `consented_at`, a lifetime equal to the 15-minute magic link), so the evidence survives opening the email on another device. "Sign in" mode writes no row; an address with no account comes back as `AGE_NOT_CONFIRMED` and is shown as "no account yet".

### 3. Email (owner decision Q2: Brevo)

- Brevo is called over `fetch` from one wrapper, `src/lib/server/email.ts`; there is no SDK. Templates are plain-text functions in fr/en/ar. The send is not awaited in the request: `waitUntil` from `@vercel/functions` keeps the invocation alive for it (a no-op outside Vercel, where the promise simply runs). A failed delivery logs the kind of mail and a status code (or `network`) and nothing else: never the address, link, token or response body.
- Transport selection fails closed. With `BREVO_API_KEY` set, mail goes to Brevo from `BREVO_SENDER`, an address on a domain verified in Brevo with SPF and DKIM. With it empty, a file transport writes the rendered mail, link included, to the git-ignored `tests/e2e/.mail/`, and only when `NODE_ENV` is exactly `development` or `test` or `JISR_EMAIL_FILE_TRANSPORT=1`; anything else throws `AuthEmailTransportNotConfigured`, so a mail that cannot leave the process fails visibly instead of looking sent. `JISR_EMAIL_FILE_TRANSPORT` exists for the e2e run and is never set on Vercel.
- One resend cooldown: 60 seconds per address and kind (`email_cooldowns (email, kind)`, kinds `magic-link` and `delete-account`; `src/lib/server/email-cooldown.ts`). The claim is one `INSERT … ON CONFLICT DO UPDATE … WHERE` on the database clock, so concurrent requests for one address cannot both win; a refusal is `429 EMAIL_COOLDOWN`. For a magic link the claim is taken once, in Better Auth's `hooks.before` for `/sign-in/magic-link`, before the plugin writes its verification row, which covers the sign-in action and a direct POST. For a deletion email it is taken inside `sendDeleteAccountVerification`, which Better Auth runs in the background and whose errors it swallows, so that endpoint still answers "sent" after a refused claim or a failed send (an unused `delete-account` verification row then stays until the account is deleted). The UI therefore never claims delivery. The cooldown lives in our code because Better Auth's limiter needs the client IP and we record none. Since the security pass (todo 28) the row is keyed by mailbox (`cooldownKey`: a `+tag` is dropped, and Gmail dots too, for the key only, never for the stored or sent address), and every claim also takes one unit of a global daily ceiling, `AUTH_EMAILS_PER_DAY` = 250 across all addresses and kinds (`auth_email_days`, one counter row per UTC day, the same single-statement claim; under Brevo's free quota of about 300 a day), refused with the same `429 EMAIL_COOLDOWN`. The mailbox cooldown is claimed first so a refused request never spends the day's budget. The last `AUTH_EMAILS_RESERVED_FOR_DELETION` = 20 sends of the day are kept for deletion confirmations: sign-in and sign-up links stop at 230 on the same counter (a kind-specific `WHERE sent < limit`, still one atomic statement), deletion emails may use all 250. Trade-off: anyone can still spend the 230 sign-in sends with made-up addresses and block new sign-ins until UTC midnight, but no longer an erasure request (Better Auth swallows a refused deletion send, so a blocked one would fail silently); 20 deletion emails a day is far above the expected rate, and a sustained flood is an operations alert (Brevo usage, `docs/ops`), not something the app can tell apart from real traffic without IPs. The magic-link hook answers `400 INVALID_EMAIL` for a malformed or oversize address before any claim or verification row.
- Magic links last 15 minutes, are single use and are stored hashed (`storeToken: "hashed"`). A cooldown-refused request still refreshes the pending row's `consented_at` and expiry, because the row is written before the claim. The row only vouches for a version that is compared at admission, so admission is unaffected; the point is on the security pass list.
- Mail from `jisrr.org` (the owner's domain, already the site's production origin) needs that domain verified in Brevo, and the Free plan's 300 emails a day bound sign-ins and deletion requests per day.

### 4. The `jisr.auth` hint and the browser cache

- Pages are static (ADR 0006), so a page cannot read the session while rendering. A browser that has signed in holds a `jisr.auth` hint in localStorage (`src/lib/auth/session-hint.ts`); a guest has none, makes no auth request, loads no auth or sync chunk and prefetches no auth route (sign-in entries are buttons that navigate on click, never prefetched links). The hint means only "this browser signed in": the session cookie is HttpOnly and the server is the only judge. A server answer of "no session" clears the hint.
- Magic-link sign-in is confirmed on a page (todo 28, F3, ruling Q16). Better Auth 1.7.7 verifies a magic link only on `GET /magic-link/verify?token=…` (`plugins/magic-link/index.mjs`: `method: "GET"`, token in the query), which signs in whoever opens the URL: a mail scanner that prefetches it spends the token, an attacker's link opened by a visitor signs the visitor into the attacker's account (login CSRF), and the token reaches host request logs. The emailed link is built by us: `/[locale]/sign-in/confirm#token=…&mode=…&return=…` (`signInConfirmPath` in `src/lib/auth/callback-urls.ts`), with an empty query. The static, `noindex` page reads the fragment, strips it from the address bar at once and signs in only when the student presses "Sign in" or "Create my account" (wording from `mode`, which the server sets to `signup` only for a signup the Server Action marked). It shows no address: the page cannot know it without asking the server about the token, and a fragment value is forgeable. The button posts `{ token }` as JSON to `POST /api/auth/magic-link/confirm`, our plugin endpoint (`src/lib/auth/magic-link-confirm.ts`), which refuses while accounts are off, runs Better Auth's `formCsrfMiddleware` (a cross-site navigation is refused, and any browser request must come from a trusted origin even without a cookie), then runs the plugin's own verify handler as a plain function call with the token (the pattern Better Auth uses for `POST /delete-user` with a token), so token consumption, user creation through the admission hook (which sees `/magic-link/confirm` as the path) and session creation stay the library's. The inner call's `Set-Cookie` is carried onto the real response, and a verify failure (its redirect to `?error=<code>`) becomes `400 { code }`; the page then hands the code to the sign-in form's existing error states (`INVALID_TOKEN` and the rest as "link failed", `AGE_NOT_CONFIRMED` as "no account yet"), shows "accounts unavailable" for `ACCOUNTS_DISABLED`, and keeps the button for a retry after a network failure. `GET /magic-link/verify` is closed by `hooks.before` (404, token untouched), like `GET /delete-user/callback`. The auth instance states `advanced.disableOriginCheck: false`, the production default, because Better Auth turns origin and CSRF checks off under `NODE_ENV=test` and the suites must exercise the production behaviour. This retires ruling Q11 (token in request logs) and replaces the HttpOnly-nonce launch gate: the link no longer signs in on its own. A student who presses the button on an attacker's link is still signed into the attacker's account; the welcome landing's confirmation, which names the account by a masked address before any import (decision 7), remains the guard for the student's data.
- Every redirect-based sign-in (magic link on any device, Google) completes on one landing, `/[locale]/welcome?return=…`. One zod-free builder, `src/lib/auth/callback-urls.ts`, makes every callback URL, a contract test pins the call sites, and a return path may only be a plain path under a known locale.
- While the hint is set, the stores show and change an account cache under `jisr.account.` (`saved`, `plan`, `profile`, `profile-draft`) and neither read nor write the guest keys (`jisr.profile`, `jisr.saved`, `jisr.plan`, `jisr.profile-draft`), which therefore hold only unclaimed guest data. Rules: sign-out removes `jisr.auth` and `jisr.account.*` only, so unclaimed guest data survives; a fresh sign-in clears `jisr.account.*` before it sets the hint, so one account's cache is never shown under another session; Clear my data removes every `jisr.` key except `jisr.auth` (signed in, it first clears the account's rows with `clearAccountData`, then the device; signed out it behaves as it always did); a completed account deletion removes every `jisr.` key, the hint included, because the student asked to erase everything.
- Guest copy does not change: signed-in wording lives in new `*SignedIn` message keys picked by the hint, and the golden fixture `tests/fixtures/i18n/guest-copy-golden.json` pins the guest strings.

### 5. Server-authoritative sync (owner decision Q1)

When signed in, Postgres is the source of truth and localStorage is a cache. The planner recommended a local-first mirror; the owner chose server-authoritative on 2026-10-13 so that a second device is never behind.

- The server stores operations, not documents. Saved programmes are rows keyed `(user_id, slug)`; plan ticks are rows keyed `(user_id, program_slug, step_id)`. Four idempotent Server Actions change them: `saveProgram` and `unsaveProgram`, `setStepDone` and `forgetProgress` (`src/lib/server/account-actions.ts`). Two devices that edit different items never overwrite each other; for the same item the last operation to reach the server wins, and every other item is untouched.
- The profile is one document with an integer `revision`. `saveProfile(profile, expectedRevision)` is a compare-and-set: `UPDATE … WHERE revision = expected`, with no lock (Postgres re-evaluates the WHERE after a concurrent commit, so of two writers holding one revision exactly one matches). A mismatch returns `{ ok: false, error: "conflict", current }`; the profile form keeps the student's values and offers "use the other device's version" or "keep mine", which resubmits against the new revision. It never overwrites silently. Revisions are monotonic per user: `user_data_state.profile_revision` (migration `drizzle/0001_young_caretaker.sql`) keeps the highest revision a deleted profile had, and a new profile row starts above it under the user lock, so a stale device always gets `conflict`.
- Every mutation is an optimistic local update, then the Server Action, then a reconcile from the action's answer. Operations are queued per store and sent in order. A failed operation rolls back that operation only and raises a visible notice (failed, saved limit, plan limit, signed out, consent required, profile reloaded). A held profile conflict lives in memory only and is lost on reload.
- No socket, polling or queue. `loadAccountData` (one repeatable-read, read-only transaction) runs when the sync chunk loads, which is once per full page load of a signed-in browser (the hint gates the chunk), on sign-in, and when a tab returns after more than 60 seconds hidden (`REHYDRATE_AFTER_HIDDEN_MS`, `src/lib/account-sync/visibility.ts`); other tabs follow writes through the `storage` event, and hydration takes the server's values. Budget: a signed-in page load costs about two function invocations (one session lookup, one `loadAccountData`) plus one per save, tick, report or profile save; a guest costs none.

### 6. Locks, caps and the action boundary

- `lockUser` takes `SELECT … FROM "user" WHERE id = $1 FOR UPDATE` (`src/lib/server/account-store.ts`) and serialises everything that must see another writer's effect: the saved-programme cap of 12 (`saved_limit`), the plan cap of 50 programmes with ticks (refused as `invalid`, which the sync layer words as a plan-limit notice), the feedback cap of 20 reports per rolling 24 hours (`created_at > now() - interval '24 hours'`, on the database clock, `rate_limited`), the first profile insert, Clear my data and the guest import. A user whose row is gone (deleted while a session was still presented) gets `unauthenticated`. Un-saving and un-ticking take no lock.
- Every account data action (`loadAccountData`, `saveProgram`, `unsaveProgram`, `setStepDone`, `forgetProgress`, `saveProfile`, `createFeedbackReport`, `clearAccountData`, `importGuestData`) runs `requireAccountReady()` inside `guarded()` before it parses its input. `guarded` logs only the action name and SQLSTATE and throws a fixed message, because Drizzle errors carry the statement's parameters (the profile, the address). Input bounds are tighter than the column sizes; the ones client code needs live in the zod-free `src/lib/constants.ts`. Server Actions live only in `src/lib/server/` with a `"use server"` prologue, and `tests/lib/client-imports.test.ts` enforces that location and the Zod-free rule for everything a browser can reach.

### 7. Guest import

- `importGuestData(payload, mode)` (`src/lib/server/import.ts`) runs in one transaction under `lockUser`. `"auto"` proceeds only when the account holds no data and has no import marker (`user_data_state.imported_at`); otherwise it answers `has_server_data` and the student chooses between keeping the server's data and replacing it with this device's (`"replace"`, which raises the profile revision so another device's next save conflicts). Two concurrent `"auto"` imports have exactly one winner (`tests/db-race/import.test.ts`).
- An import claims and afterwards clears exactly `jisr.profile`, `jisr.saved` and `jisr.plan`; the draft, the hint and the account cache are never touched.
- Revised on 2026-10-15 after the security review: the welcome landing never imports without an explicit confirmation that names the signed-in account by a masked address. A magic link signs in whoever opens it (login CSRF), so a silent import would let an attacker's link upload a guest's profile to the attacker's account. A masked address alone is weak against a look-alike address, so binding the magic-link sign-in to the browser that asked for it (an HttpOnly nonce) was a launch gate (decision 14); the security pass first replaced it with the confirm page (decision 4, todo 28 F3, ruling Q16), so opening a link no longer signs anyone in, and then added a soft browser-bound nonce (ruling Q19, todo 28): the browser that asked for a link keeps an HttpOnly cookie whose random value is stored only as a hash bound to the link's token, and when the confirm does not match, the sign-in still completes (a cross-device sign-in must keep working) but the landing never offers the guest import and shows a "this browser did not ask for this sign-in link" warning with a Sign out button. Residual: a victim who presses the confirm button on an attacker's look-alike-address link can still be signed into the attacker's account. The landing withholds the guest import for every landing of that tab until the student signs out (the session flag is read, not consumed, so a reload keeps the warning), and an import always needs the student's own click; the masked address is the second guard.

### 8. Per-fact feedback (owner decision Q3)

A signed-in student can report a fact as outdated where they read it. The button is opt-in on `SourceBadge` (`report`) and appears on journey fact surfaces only (programme page facts, match reasons, cost lines, compare cells, scholarship facts, plan steps), never on the home demo, the trust band or the guides. A report is a `feedback_reports` row: the `FactRef` fields (`record`, `path`, `source_url`), the `snapshot_version` the student was reading and an optional note of at most 500 characters (the current UI sends none), capped at 20 per user per rolling 24 hours (decision 6). The button's code loads only with a hint or on a click, a signed-out click goes to the sign-in surface with a return path, and `consent_required` routes to the welcome landing. The owner reads reports in the database; there is no admin UI (ADR 0003).

### 9. Rights: export, deletion and what is never stored

- Export: `GET /api/account/export` (`src/app/api/account/export/route.ts`, logic in `src/lib/server/account-export.ts`) returns one pretty-printed JSON attachment with `Cache-Control: no-store`. Every table is read with a named-column allow-list inside one repeatable-read transaction, so session tokens, IP address and user agent, verification rows, OAuth tokens and the password column are never selected. It needs a session but not current consent: the right of access must not wait behind re-consenting, and deletion follows the same rule. It answers `401 UNAUTHENTICATED` without a session and `403 ACCOUNTS_DISABLED` before any session or database work. The `email_cooldowns` timestamp is not exported: it is a rate-limit marker, listed in the privacy notice and erased with the account. The account page (`/[locale]/account`, static and `noindex`) hosts the download, the deletion request and the consent record.
- Deletion is Better Auth's `deleteUser` with an emailed confirmation, because Google-only accounts have no password and email is the only proof. The link in the email is built by us: `/[locale]/account/delete#token=…`. It lands on a page with an explicit button, because mail scanners prefetch GET links and a GET must never delete. The token rides the fragment, so it never reaches a request log, a `Referer` header or analytics, and the page strips it from the address bar at once. Completion is a POST (`authClient.deleteUser({ token })`) that needs the session cookie, Better Auth's origin check and the click. Better Auth's own `GET /delete-user/callback`, which deletes on a plain GET, is closed (404 from `hooks.before`) and never emailed. A `hooks.after` expires the session cookie on the real response, because Better Auth calls its callback as a plain function and the `Set-Cookie` of that inner call is dropped.
- Erasure: Better Auth removes the user, session and account rows, and the app tables cascade from `user.id`. `eraseAccountResidue` (`src/lib/server/account-erasure.ts`) runs in `beforeDelete` and again in `afterDelete` and removes what Better Auth leaves: every verification row that names the user (value is the user id; magic-link rows by address; OAuth state rows by user id or address, parsed with `pg_input_is_valid(…, 'jsonb')` so one malformed row cannot fail a deletion), and the `email_cooldowns` and `pending_signups` rows for the address. `pg_input_is_valid` needs Postgres 16 or newer; Neon runs 18. Once the server confirms, the device removes every `jisr.` key.
- Never stored: the IP address (Better Auth's IP tracking is off, which also switches off its IP-keyed limiter, hence decision 3) and the session user agent (a `session.create.before` hook nulls both fields, and no feature reads them; minimisation beat disclosing them in the notice). OAuth access and refresh tokens are encrypted with the auth secret and the Google ID token is nulled. Better Auth does store Google's `name` and `picture`, which nothing uses; the notice discloses them and `mapProfileToUser` could drop them. Session lifetime is Better Auth's default of 7 days and is not pinned in code.
- Logs: the only sink is `console` (Sentry is not wired). Account actions log the action name and a SQLSTATE through `guarded()` because Drizzle puts a failed statement's parameters in its error; the mail sender logs a kind and a status. Better Auth's own logger and better-call print raw errors (a failed session read carries the token, a failed insert the address), so `logger.log` and `onAPIError.onError` (`src/lib/auth/log.ts`) replace both: the message with addresses and URLs blanked, an error's name and code, never an object. `tests/lib/privacy/no-pii.test.ts` drives the real flows on PGlite with every console method recorded and fails on any address, token, cookie, user agent, grade or nationality; it also proves it catches a deliberate offender, and it fails if a Sentry or instrumentation file appears without joining the suite. The magic-link token no longer reaches request logs: since the security pass (todo 28, F3) it rides the confirm page's fragment and a POST body (decision 4), which retires ruling Q11.

### 10. Slug aliases (refines ADR 0005 item 11)

- Programme and institution records may carry `formerSlugs`. `pnpm data:check` rejects a former slug that equals a live slug or another record's former slug, rejects cycles and duplicates, and flattens chains. The build publishes a `formerSlug → current slug` map as `aliases` in the manifest (`src/data-schema/snapshot.ts`, with the hand-written client twin in `src/lib/snapshot/manifest.ts` and a differential test). One function, `resolveProgramSlug` (`src/lib/snapshot/resolve-program-slug.ts`), resolves a slug everywhere (plan, compare, saved list, `SaveProgramButton`, import); an unknown slug comes back unchanged, so the existing missing-programme view still decides. A saved entry keeps the slug it was saved under as its identity, and old plus new slugs are deduplicated for display and import. Redirects never go in `vercel.json` (`tests/vercel-config.test.ts` forbids them) or in `next.config`: the rename and its redirect travel in the same data release.
- Each former slug is a static page (`programStaticParams` adds it; `dynamicParams` stays false) that calls `redirect()` from `@/i18n/navigation`, and Next prerenders that as a real HTTP 307 with a `Location` header, not a meta refresh. **Decision: keep 307.** No slug has ever been renamed (the data rule is still "do not rename"), so the mechanism is proven on `xx-test-*` fixtures only. A 307 is not cached, so an alias that proves wrong, is reverted or is later reassigned is corrected on the next request, while a browser or crawler caches a 308 indefinitely and no deploy can recall it. The price of 307 is that search engines pass less to the new URL, which does not matter here: former slugs are absent from the sitemap (`programSlugs` lists live slugs only) and their page metadata is `noindex`. Revisit: once a real rename has lived through one full data cycle without being reverted, switch the alias page to `permanentRedirect` (next-intl's `createNavigation` already returns it; `src/i18n/navigation.ts` must export it). Re-check the status in the page's `.meta` file after every Next upgrade.

### 11. Pre-account tables and retention

`pending_signups` and `email_cooldowns` are keyed by normalised address and have no user foreign key, because they exist before an account does. Rows expire lazily: an expired pending row is ignored (`readPendingSignup`), a cooldown row simply stops blocking, and there is no sweeper (no worker, ADR 0003). The gap: a row for an address that never becomes an account is overwritten by that address, erased with its account or removed on request, and is otherwise never deleted. Decision, done in the security pass (todo 28, F4): every granted auth email send (`claimAuthEmailSend`) deletes `pending_signups` rows past `expires_at`, `email_cooldowns` rows older than 24 hours and `auth_email_days` rows of past UTC days, best effort (a failed purge is logged by SQLSTATE and does not stop the send), still with no worker. The privacy notice says these rows are deleted, once expired, the next time Jisr sends a sign-in or deletion email, that there is no scheduled clean-up, and that they are removed on request (ruling Q18); an idle stretch only delays the purge to the next send.

### 12. Test policy: PGlite and a real Postgres

PGlite behind a TCP socket (`scripts/db/harness.ts`) backs the fast suites (schema, actions, export, deletion, e2e). It has one connection, so a test of concurrent behaviour proves nothing on it. Every race or transaction spec lives in `tests/db-race/` and needs `TEST_POSTGRES_URL`: the cap races (`saved-cap`, `feedback-cap`), profile compare-and-set and revision monotonicity (`profile-cas`, `profile-revision`), the double import (`import`) and the cooldown claim (`email-cooldown`). CI runs them in a `db-race` job against a `postgres:18` service container, matching Neon's major version, and a guard step fails the job if the JSON report shows a skipped spec or no passing one. Locally they are reported as skipped, with the reason in the suite title, and never counted as passed. Each spec creates its own throwaway `race_<hex>` database, not a schema, because drizzle-kit writes `"public"`-qualified foreign keys and enums. Rule: any claim of atomicity, ordering or locking needs a spec there; PGlite specs prove sequential behaviour only.

### 13. Row provenance

A saved programme and a feedback report store the programme slug and the `snapshot_version` they were made against, with no foreign key to reference data (ADR 0003, `.claude/rules/database.md`). A plan tick (`checklist_progress`) stores the slug and the step only: it has no `snapshot_version` column, because a tick is a student's own progress, not a claim about a snapshot. `snapshotVersion` is provenance, never a pin: nothing fetches a snapshot by it, programmes are always resolved against the current manifest, and export and import keep the stored value untouched. The UI copes with a slug that no longer exists through the alias map and the existing missing-programme view.

### 14. Launch gates

Accounts do not switch on until the owner has: filed the CNDP declaration (ADR 0004 section 6; this ADR does not claim it has been filed); filled `[CONTROLLER NAME]` and `[CONTACT EMAIL]` in the privacy notice and terms; had the notices, the Arabic copy and the processor terms reviewed; created the Neon project in Frankfurt (Postgres 16 or newer, database time zone UTC, because the generated auth tables use `timestamp` without a zone and the pool pins each session to UTC) and run `pnpm db:migrate` on a staging branch first; had Brevo approve the account and verified `jisrr.org` there (SPF and DKIM, DMARC recommended) with `BREVO_SENDER` on it; set `BETTER_AUTH_URL` (the live origin), `BETTER_AUTH_SECRET`, the Google credentials and the Brevo key in the Vercel Production scope and registered the Google redirect URI `<origin>/api/auth/callback/google`; and seen the security pass closed. The last step is `ACCOUNTS_ENABLED=true` in the Production scope, then a redeploy.

The security pass is a `security-review` skill run plus an Opus review over the auth hooks, admission, import, export and deletion (plan todo 28), recorded in `docs/ops/security-review-accounts.md`. It carries these items from the build:

- bind the magic-link sign-in to the initiating browser: done as the confirm page (decision 4, todo 28 F3, ruling Q16) plus a soft HttpOnly nonce (ruling Q19, todo 28, `src/lib/auth/magic-link-nonce.ts`): the browser that asked for the link keeps an HttpOnly cookie holding a random value, only its hash is stored (bound to the link's token, in a second `verification` row), and a mismatch still signs in — cross-device keeps working — but the landing withholds the guest import and warns;
- the lazy purge of pre-account rows, decision 11;
- the magic-link token travelled in the verify URL's query (`plugins/magic-link/index.mjs` sets it with `searchParams.set("token", …)`) and reached Vercel request logs: retired by the confirm page (decision 4, todo 28 F3; ruling Q11 no longer applies);
- a deletion response lost in transit, or an `afterDelete` sweep that throws after the user row is gone, leaves the confirm page failed, the retry gets 401 and the device keys are not cleared;
- a browser that still holds `jisr.auth` after the flag is switched off again shows its cached data until the hint is cleared;
- a refused send refreshes `consented_at` (decision 3), and Google's `name` and `picture` are stored unused (decision 9).

The owner-facing rows for these gates live in `docs/ops/prelaunch-checklist.md`; the new usage checks (Brevo's daily cap, account-driven function invocations, Neon compute) in `docs/ops/limits-runbook.md`.

## Alternatives considered

- **A local-first mirror** (localStorage stays authoritative, the server keeps a copy): the planner's recommendation, rejected by the owner (Q1) because a second device could be behind or overwrite the first.
- **Whole-document writes** (`putSavedList`, `putPlanProgress`, an unconditional `saveProfile`): the first plan, replaced during review because a phone and a laptop would silently overwrite each other (last write wins). Per-item operations and a compare-and-set revision replaced them.
- **Websocket, polling or queue sync:** rejected (ADR 0003 "not built", Hobby budget); hydration on load and on tab return is enough for one student on two devices.
- **`validateUserInfo` as the admission gate:** unsatisfiable, decision 2.
- **A cookie, or the plugin's `metadata`, to carry consent for magic links:** a cookie fails when the email is opened on another device, and `metadata` never reaches user creation. The pending row works on any device.
- **Passwords and more providers:** out (`.claude/rules/auth.md`: no password-reset email volume).
- **Brevo's SDK:** one `fetch` call needs no dependency. Brevo itself was the owner's choice (an EU provider with a free tier).
- **Better Auth's own rate limiter:** it needs IPs, which we do not record, so the throttle is `email_cooldowns`.
- **Deleting through Better Auth's GET callback, or putting the token in the query:** a GET must not delete, and a query token reaches request logs, decision 9.
- **Disclosing the session user agent instead of blanking it:** nothing reads it, so it is not kept.
- **Redirects in `vercel.json` or `next.config`:** forbidden, decision 10. **A 308 now:** deferred to the first real rename, decision 10.

## Consequences

- Positive: the guest journey is untouched (guest strings, keys and traffic are pinned by the golden fixture and the guest e2e specs); a merge can never launch accounts; two devices converge without a socket and a failed save is visible; the caps, the compare-and-set and the double import are covered by specs that run against a real Postgres in CI; a deletion leaves nothing that names the student in the database or on the device; no IP address or device information is stored.
- Negative: the account layer adds client JavaScript (the eager store facade, the report slot on `SourceBadge`, the lazy menu loader) against a ratchet that had almost no room (ADR 0008); any raise is the owner's decision, with a written reason in its own commit (plan todo 27). Function invocations now grow with signed-in students, which the Hobby cap and the monthly check must watch. Brevo's 300 emails a day bound sign-ups and deletion requests. Turning accounts on or off for the static pages takes a deploy. Addresses that never become accounts leave expired rows until the next auth email purges them. Every magic-link sign-in takes one more click, on the confirm page. Arabic copy is still a machine draft, and session length follows a library default.
- Signed-in e2e: `pnpm test:e2e:accounts` (`playwright.accounts.config.ts`, `tests/e2e-accounts/`) is the only place `ACCOUNTS_ENABLED` is set (with test-only auth secrets and the file email transport, in that webServer's env), because the static pages read the switch at build time and so need their own build; it shares `.next` with the guest suite, so run them one after the other.
- Neutral: "no admin UI" holds (the owner reads feedback in SQL); `user.role` stays `student`; Sentry is still deferred (ADR 0011 section 8), so the privacy notice names it as not in use.

## How to revisit

ADRs are immutable once committed. If this decision turns out wrong, write a new ADR that supersedes this one — don't edit this in place. Triggers: Brevo's free quota or terms change, or a day reaches 60% of the cap; Function Invocations reach 60% of the Hobby cap (`docs/ops/limits-runbook.md`); the first real slug rename has lived through a data cycle (307 to 308); a Better Auth or Next upgrade changes anything listed under "Facts checked" (re-check them before upgrading); the privacy notice changes (bump the consent version); Sentry is enabled; the owner adopts a retention policy for inactive accounts.
