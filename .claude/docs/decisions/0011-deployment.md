# ADR 0011 — Deployment of the guest release: Vercel Hobby, CI-gated production deploy, safe-by-default indexing

**Status:** Accepted
**Date:** 2026-10-08

## Context

The guest release (no accounts, no database) is ready to be hosted. ADR 0004 chose Vercel Hobby (fra1) and listed a "Before launch" checklist, but its Vercel figures came from secondary sources of 2026-09-29. This ADR records how the site is deployed, the facts verified on 2026-10-08, and the decisions that follow. Spec: `docs/superpowers/specs/2026-10-08-deployment-design.md`. Runbooks: `docs/ops/deploy.md`, `docs/ops/limits-runbook.md`, `docs/ops/prelaunch-checklist.md`.

Constraints: one developer; zero recurring cost; the repository is private on GitHub Free, where branch protection is unavailable ("Upgrade to GitHub Pro or make this repository public"); no Vercel, GitHub or DNS resource is created by the repository; nothing here may raise the client JavaScript ratchet in `tests/e2e/support/js-budget.ts`.

### Facts verified on 2026-10-08

Sources: https://vercel.com/docs/limits, https://vercel.com/docs/plans/hobby, https://vercel.com/docs/limits/fair-use-guidelines, https://vercel.com/docs/cli/deploy, https://vercel.com/docs/project-configuration, https://vercel.com/docs/instant-rollback, https://vercel.com/docs/deployment-protection, https://vercel.com/docs/notifications, https://vercel.com/docs/pricing/manage-and-optimize-usage.

- Hobby monthly included usage: CDN Requests 1,000,000; Fast Data Transfer 100 GB; Fast Origin Transfer 10 GB; Function Invocations 1,000,000; Active CPU 4 hours; Provisioned Memory 360 GB-hours.
- Hobby builds: 45 minutes, 8 GB memory, 2 vCPU; 100 deployments per day. A CLI deployment of source files is limited to 15,000 files and 100 MB; whether these caps also apply to the built output that `--prebuilt` uploads is unverified. The Vercel API allows 5,000 uploads per day on Hobby.
- Over a limit, a Hobby project waits 30 days in most cases (Hobby has no billing cycles) and a paused deployment answers `503 DEPLOYMENT_PAUSED`; Vercel emails details and next steps. Nothing is billed. How the project resumes is not verified here: follow Vercel's email and dashboard notice.
- Hobby gets Vercel's automatic usage notification emails, which are not configurable; Spend Management and configurable thresholds are Pro-only.
- Fair use: Hobby is non-commercial. Commercial use includes any way of requesting or processing payment, advertising a product or service, being paid to create, update or host the site, affiliate links as the primary purpose, and ads. Asking for donations is explicitly not commercial use.
- Password Protection is not available on Hobby (Pro add-on); Vercel Authentication is. Under the scope Standard Protection, generated deployment URLs and previews need a Vercel login while production domains, including the auto-assigned `<project>.vercel.app`, stay public; the scope All Deployments would also protect production.
- After an Instant Rollback Vercel turns off auto-assignment of production domains, so later deployments do not go live until the rollback is undone (**Undo Rollback** or `vercel promote`). Hobby can roll back only to the immediately previous deployment.
- `vercel deploy --archive=tgz` is documented to minimize the number of files uploaded and avoid upload limits when a deployment has thousands of files; it may be slower because per-file upload caching is lost.
- `vercel pull`, `vercel build --prod`, `vercel deploy --prebuilt --prod` is Vercel's documented Actions flow. With `--prebuilt` the system variables (`VERCEL_ENV`, `VERCEL_URL`) are not injected at build time, so nothing may depend on them being present at build time.
- Measured locally on 2026-10-08 on the Task 7 branch (about 1,100 programmes; the data keeps growing): the default `.next` output is about 1.5 GB with about 24,000 files, mostly one HTML file, one RSC payload and segment files per programme and locale. The snapshot version changes with every data build. Exact and current figures (programme count, file counts, sitemap size, build time) are kept in `docs/ops/deploy.md`, `docs/ops/limits-runbook.md` and `docs/ops/prelaunch-checklist.md`, not here.

## Decision

### 1. Release flow: Vercel previews, production by a CI-gated Actions job
- Pull requests get a protected preview from Vercel's Git integration (Vercel Authentication on; previews are also non-indexable).
- Production is deployed only by the `deploy` job in `.github/workflows/ci.yml`: `needs: [verify, e2e]`, push to `main` only, `vars.DEPLOY_ENABLED == 'true'`, `concurrency: deploy-production` without cancelling, `timeout-minutes: 30`. It runs `vercel pull --yes --environment=production`, `vercel build --prod`, `vercel deploy --prebuilt --archive=tgz --prod`, writes the deployment URL to the step summary, and runs `pnpm ops:smoke` against `vars.SMOKE_URL` when that is set.
- `vercel.json` sets `git.deploymentEnabled: { "main": false }` so Vercel does not also deploy `main`.
- Until the owner sets `DEPLOY_ENABLED` the job is skipped; once enabled, a secrets pre-check fails fast on purpose when `VERCEL_TOKEN`, `VERCEL_ORG_ID` or `VERCEL_PROJECT_ID` is missing. Owner order: secrets, then `DEPLOY_ENABLED=true`, then (after the first successful deploy and DNS) `SMOKE_URL`.
- Least privilege in the workflow: `permissions: contents: read`; checkout with `persist-credentials: false`; the token is a step-level environment variable (`VERCEL_TOKEN`), never a `--token` argument, and only on the pre-check, `vercel pull` and `vercel deploy`. `vercel build` runs **without** the token because the build executes project scripts whose child processes would inherit it. If the first deploy fails at Build with an authentication error, give that step the token and record the change in a new ADR.
- The Vercel CLI is installed with `npm install --global vercel@latest`, unpinned, following the project rule of latest stable packages. Supply-chain trade-off accepted: a compromised CLI release would run with the token.
- The smoke step targets the public production domain in `SMOKE_URL`, not the deployment URL, because Deployment Protection covers `*.vercel.app` deployment URLs.
- `--archive=tgz` is the first mitigation for the size of the output (about 24,000 files against 5,000 uploads per day on Hobby). It is documented by Vercel together with `--prebuilt` but unverified in this repository until the first deploy.
- Rollback: Vercel Instant Rollback (dashboard) or `vercel rollback`, Hobby only to the immediately previous deployment. **A rollback switches off automatic production assignment**: later deployments (and a green deploy job and smoke test against the public domain) do not go live until **Undo Rollback** or `vercel promote <deployment-url>`. The runbook says so in `docs/ops/deploy.md` section 7.

### 2. No branch protection; residual risk accepted
Branch protection is unavailable (private repository on GitHub Free), and so are GitHub Environments with branch restrictions. The release gate is the job order in Actions. **Residual risk:** a pull request from a branch of the same repository runs its own, possibly modified, `ci.yml` with the repository secrets, so write access to the repository equals deploy access, as it already equals push to `main`. Mitigation: a team-scoped Vercel token with an expiry of at most 1 year (calendar reminder); rotate it when a collaborator is added or the repository is made public. Making the repository public was considered and is not recommended yet: thousands of tracked `data-staging/` files (count in `docs/ops/deploy.md` section 11) are unaudited and include fetched third-party page text; the project is closed-source by decision; there is no LICENSE; a history scan found no secrets. The design works unchanged if the repository becomes public later; then branch protection requiring `verify` and `e2e` is added and the audit comes first.

### 3. Safe-by-default indexing
`src/lib/site-env.ts` validates three optional variables when `next.config.ts` loads (a malformed value fails the build): `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_SNAPSHOT_BASE_URL`, `NEXT_PUBLIC_GOATCOUNTER_URL`. A build is indexable only when `NEXT_PUBLIC_SITE_URL` is set and `VERCEL_ENV !== 'preview'`. The variable is set in the Vercel **Production scope only**, so previews, which have no value, are never indexable without relying on a system variable that `--prebuilt` does not provide. Not indexable means: `robots.txt` `Disallow: /`, `X-Robots-Tag: noindex, nofollow` on all responses, no canonical or alternates, an empty sitemap, and no analytics script. Indexable means canonical, hreflang (`fr`, `en`, `ar`, `x-default` = `fr`), basic Open Graph and Twitter metadata, an allowing `robots.txt` and the sitemap. `/matches`, `/plan` and `/compare` are `noindex, follow` and absent from the sitemap in every build: they are static shells around a personal client area (thin content, nothing about the student in the HTML). Apex is canonical and `www` redirects to it once a domain is chosen. Limit of this design: `Disallow: /` in `robots.txt` stops compliant crawlers from fetching a page, so they never see its `X-Robots-Tag` header or meta tag, and an unprotected non-production host could still appear in search results as a bare URL. Previews are protected by Vercel Authentication, so nobody should rely on `noindex` alone.

### 4. Security headers; structural CSP
`src/lib/security-headers.ts` adds on all routes: `Strict-Transport-Security: max-age=63072000`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a `Permissions-Policy` denying camera, microphone, geolocation, payment, usb and browsing-topics, and `Content-Security-Policy: frame-ancestors 'none'; base-uri 'self'; object-src 'none'; form-action 'self'`. The existing snapshot cache rules (immutable shards, `no-cache` manifest) are unchanged. `X-Frame-Options` is omitted because `frame-ancestors` covers it.
- **No `script-src`.** Every page is static, so there is no per-request nonce, and Next's inline bootstrap scripts would force `'unsafe-inline'`, which adds no protection. Revisit when Next supports hash-based or SRI-based CSP for statically rendered pages.
- **HSTS without `includeSubDomains` or `preload`.** Both are hard to undo and unsafe before the production domain is final. Revisit after the domain is final and every subdomain in use serves HTTPS.

### 5. Proxy narrowed to `/` and locale-less paths
Every matched request is a Vercel Function invocation (Hobby: 1,000,000 a month). The matcher in `src/proxy.ts` now also skips locale-prefixed paths (`/fr`, `/fr/...`, `/en...`, `/ar...`), which are served from the static prerender. The proxy runs only for `/` and locale-less paths, where it redirects. Hreflang comes from page metadata and the sitemap, with `alternateLinks: false` in `src/i18n/routing.ts`. A test keeps the locale alternation in the matcher equal to `routing.locales`.
- **Consequence:** the proxy no longer sets next-intl's locale header on locale-prefixed paths, so every dynamically rendered future `[locale]` route must call `setRequestLocale(locale)` itself (the existing pages and layout already do).
- **Unverified on Vercel:** that the platform router honours the compiled matcher as `next start` does, and that `/FR` (uppercase) behaves as locally. Owner check after the first deploy: `curl -sI https://<url>/FR`, `curl -sI https://<url>/fr/x`, and the function-invocation count in the dashboard.

### 6. Sitemap composition
`src/app/sitemap.ts` lists the home, profile and scholarships paths and every programme page, each in all three locales with hreflang alternates (about 3,400 URLs when this was written, far under the 50,000 limit). `pnpm ops:smoke --expect=indexable` checks its structure (more than 9 URLs, a multiple of 3, every programme with its `fr`, `en` and `ar` twin, `x-default`, no personal-shell URLs) rather than an absolute size; `--min-urls=N` adds a floor.

### 7. GoatCounter: inline loader and a closed event list
`src/components/analytics-loader.tsx` is a server component that emits one inline script (zero client bundle). It renders only in an indexable build with `NEXT_PUBLIC_GOATCOUNTER_URL` set. It honours Do Not Track and Global Privacy Control, waits for the page `load` and then for idle time (`requestIdleCallback` with a 5 s timeout; 2 s `setTimeout` fallback), and injects `https://gc.zgo.at/count.js` (resolved 2026-10-21: it now loads the versioned `count.v5.js` with Subresource Integrity). That is a third-party script origin and must be listed in the privacy notice. One page view is counted per full page load; client-side navigations are not counted, and journey events carry the funnel. `src/lib/analytics.ts` allows exactly five count-only events with no payload: `profile-started`, `profile-completed`, `matches-viewed`, `program-saved` (on add), `plan-opened`; each fires at most once per page load. `profile-completed` fires in create mode only; `profile-started` fires once per full load of `/profile` in create mode, so a returning student resuming a draft counts again. `count.js` itself also sends the page title, referrer, screen width and the query string with each hit; the app has no query strings and puts no profile data in titles. Setup for the owner: create a free non-commercial site at goatcounter.com (EU), set `NEXT_PUBLIC_GOATCOUNTER_URL=https://<code>.goatcounter.com/count` in the Production scope, redeploy.

### 8. Sentry deferred
Sentry is not added in this release. It would add client JavaScript against a ratchet that has almost no room: when this was measured (2026-10-08, fixture build, after the analytics change) the `/fr/matches` initial row and the programme until-idle row each had about 0.1 KB of headroom under the ratchet (current numbers in `docs/ops/prelaunch-checklist.md`). The next change to those routes needs an owner decision on the ratchet. The ratchet was not touched by this work. ADR 0004 section 3 remains the plan for Sentry.

### 9. `.vercelignore` and `--prebuilt`
`.vercelignore` guards only a manual `vercel deploy` from a checkout against the CLI source-upload caps (15,000 files, 100 MB). It has no effect on Vercel Git builds (which clone the repository) or on `--prebuilt` deployments (which upload built output); the file says so.

### 10. Region
`vercel.json` sets `regions: ["fra1"]`. After the first deploy the owner confirms `fra1` in the dashboard and also sets Settings, Functions, region to Frankfurt as a fallback. Static files are served from the CDN everywhere regardless; the region only decides where function invocations (redirects from `/` and locale-less paths) run.

### 11. Refinement of ADR 0004 section 1
ADR 0004 is immutable; this ADR refines it:
- The request cap is now called **CDN Requests** (ADR 0004: "edge requests"), and **Fast Origin Transfer** (10 GB) was not in ADR 0004's list.
- **Donations are allowed.** Vercel's fair-use page says asking for donations is not commercial use, under an umbrella definition of commercial use as a deployment used "for the purpose of financial gain of anyone involved in any part of the production of the project". The "risk" bullet of ADR 0004 section 1 narrows accordingly: ads, affiliate links as the primary purpose, payments and being paid to create, update or host the site remain out. Sponsorship paid in exchange for placement is this project's reading of "advertising a product or service" (Vercel does not name it) and also stays out. Re-read the page before a donation link goes live.
- Hobby gets automatic, non-configurable usage notification emails; Spend Management and configurable thresholds are Pro-only. The monthly manual check and the 60% rule (`docs/ops/limits-runbook.md`) are the deliberate early warning, the emails the backstop.

### 12. Unverified until the first real deployment
Listed in `docs/ops/deploy.md` section 10 and the pre-launch checklist: (1) output upload size, file count and time: about 1.5 GB and about 24,000 files, given 5,000 uploads per day on Hobby and the unverified applicability of the 15,000-file and 100 MB caps (risk number 1); (2) whether `vercel deploy --prebuilt --archive=tgz` is accepted by the CLI and how long the upload takes; (3) `vercel build --prod` without the token; (4) `npm install --global vercel@latest` on the runner; (5) `fra1` honoured with `--prebuilt`; (6) proxy matcher and `/FR` on Vercel's router; (7) Standard Protection leaving the production domain public; (8) function invocation counts against page views; (9) the GitHub-hosted runner running e2e without the local SWC workaround, and e2e never having run on Linux: if it is red on the first push to `main`, production is not deployed until it is fixed, because `deploy` needs `verify` and `e2e`; (10) the pnpm version Vercel detects from `packageManager` and `pnpm-lock.yaml` (first preview build log); (11) after the first merge with the Vercel project connected, the Deployments list shows no Git-sourced Production deployment for that commit, which proves `git.deploymentEnabled.main: false` took effect (if one appears, the gate is not holding: disable it in Settings, Git, and report); (12) Git-integration previews on a private repository may be blocked when Vercel cannot match the commit author (`Never <dagdaguihamza1@gmail.com>` on this branch) to the account: verify that email on the GitHub account or set `git config user.email` to the account's verified address.

If the upload in (1) is rejected or too slow even with `--archive=tgz`, this ADR does not solve it. Generating a subset of programme pages with on-demand rendering is not possible, because the snapshot is not traced into functions (`public/` is not available to functions; `dynamicParams = false`, ADR 0006). The real options, for a follow-up decision by the owner, are shrinking the per-page payload, or moving programme pages to incremental static regeneration with the snapshot read from a CDN URL (the `NEXT_PUBLIC_SNAPSHOT_BASE_URL` seam partly prepares this).

## Alternatives considered

- **Vercel auto-deploy of `main` through the Git integration:** simplest, but production would then deploy independently of the `verify` and `e2e` jobs, and without branch protection nothing would gate it. Rejected; previews keep the Git integration.
- **Making the repository public to get branch protection:** rejected for now for the reasons in decision 2.
- **GitHub Environments with required reviewers or branch rules:** unavailable for private repositories on the Free plan.
- **Vercel Pro:** removes the caps and adds Spend Management, configurable usage thresholds and Password Protection, but ends the free, non-commercial setup. Reserved as the contingency for a pause.
- **Cloudflare Pages for the whole site:** free egress, but the app relies on the Next.js proxy and the unified 404; it would be a larger migration without a measured need. Cloudflare R2 or Pages stays the plan for snapshots only, at 60% of a cap (ADR 0004).
- **A strict `script-src` CSP with nonces:** needs per-request rendering, which would turn static pages into function invocations; with hashes it is not supported by Next for static pages yet.
- **Relying on `VERCEL_ENV` alone to decide indexing:** not available at build time with `--prebuilt`; the Production-scope variable works on every path and `VERCEL_ENV` is only a second safeguard.

## Consequences

- Positive: production changes only after the full CI passes; previews and unconfigured builds cannot be indexed; the proxy no longer costs an invocation per page view; the headers, robots and sitemap are code with tests; analytics add no bundle weight; the owner has numbered runbooks and a smoke tool.
- Negative: write access to the repository equals deploy access until branch protection exists; the `vercel@latest` install is unpinned; the production deploy path is untested until the owner adds secrets; the output size is a real risk; the CSP has no `script-src`; a usage cap pauses the site and only a manual check warns about it; the matches and programme routes have almost no JavaScript budget left, which also keeps Sentry out.
- Neutral: the proxy's role shrinks to redirects; future dynamic `[locale]` routes must call `setRequestLocale`; no `www` redirect or custom domain exists until the owner buys one.

## How to revisit

ADRs are immutable once committed. If this decision turns out wrong, write a new ADR that supersedes this one — don't edit this in place. Triggers: the first deploy shows the output upload fails or is slow; the repository goes public or gains collaborators (branch protection, token rotation); a usage figure reaches 60% of a cap; the domain is chosen (HSTS `includeSubDomains`/`preload`); Next supports hash-based CSP for static pages; the owner decides on Sentry and the JavaScript ratchet; Vercel changes its fair-use or Hobby terms.
