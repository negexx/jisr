# Domain core: eligibility, matching, costs, checklist

- `src/domain` is **pure TypeScript** that runs in the browser: no React, Next, DB, `fs`, network or `Date.now()` (pass `now` in). Enforced by a Biome `noRestrictedImports` override — don't disable it; move the impure code out instead. Write tests first (table-driven Vitest).
- Inputs are a student profile and snapshot data (already Zod-validated); outputs are plain serialisable objects.
- Eligibility has two levels: (1) the admission route for `(origin credential country, type) → (destination, level)`; (2) program-level requirement rules. A route outcome of `not_eligible` or `foundation` short-circuits into a clear result with reasons before program rules are evaluated (the result holds only the route reason; conditions, rules and coverage are not evaluated).
- Match result: `{ programSlug, status: "satisfied" | "check" | "not_satisfied", route, reasons: Reason[] }`; each `Reason` names the requirement, the student's value and the requirement's source (`facts: FactRef[]`). Mapping to ✅ ⚠️ ❌ happens only in the UI layer.
- Semantics: `satisfied` only if every published requirement was evaluated and passed; `not_satisfied` only for a definite failure of a *published* requirement; missing data, unknown credential equivalence or unpublished thresholds → `check`. Never round an unknown up to satisfied.
- Freshness: thresholds come from `src/data-schema/staleness.ts` and are evaluated against the `now` argument. Any reason depending on a stale fact is `unknown` (with code `stale_source` unless it was already unknown for another reason, e.g. `missing_student_value`, `threshold_unpublished`), so the result is `check` with the reason "source not re-verified recently" — never `satisfied` or `not_satisfied` on stale evidence. A past deadline is never returned as upcoming ("closed, next dates not published").
- A decisive `not_satisfied` stands even when other facts in the result are stale: a fail is only produced from fresh official facts, and every result that depends on a stale or non-official fact is already `check`. Accepted by the product owner (ADR 0005, decision 2); change it only with a new ADR.
- `subject_taken` is judged on the union of the student's listed subjects and the track's curriculum: pass if the student's listed subjects satisfy `mode`; fail only when the track has a known curriculum and the union still does not satisfy it; otherwise `check`.
- Language rules: empty `acceptedTests` means any certificate is accepted (`certificateRequired: true` then needs a non-null certificate).
- Requirements are data evaluated by one rule engine, not per-university `if` chains.
- Grade rules (`overall_grade_min`, `subject_grade_min`): a student grade whose scale is not in the grading scales, or whose value lies outside that scale's `[min, max]`, is `unknown` (`missing_student_value`) before any conversion or comparison, so a typo or stale profile never yields ✅ or ❌.
- `aggregateMatchStatus([])` is `check`: no evidence evaluated is never `satisfied`.
- Costs: `estimateCost` returns a `CostEstimate` with exactly 7 `CostLine`s in fixed order (tuition, housing, food, transport, insurance, application_visa, setup), each carrying its `FactRef` (so its own `info_kind` and freshness; the tuition line is `{min, max}` from the fee's bounds (a flat fee has equal ends) and carries `incomeBased` when the range depends on household income), plus per-currency `totals` ranges (no FX conversion), `complete` (all 7 lines present), `budgetFit` and `academicYearMonths`. Never a single "exact" total. `budgetFit` is `unknown` when the budget is null, the estimate is incomplete, more than one currency is involved, or the single-currency total is in a different currency from the budget; it never affects the match status.
- Living costs assume a 10-month academic year (`ACADEMIC_YEAR_MONTHS = 10`, exposed as `CostEstimate.academicYearMonths`); monthly lines and a monthly budget are multiplied by it. Housing is often paid for 12 months, so the UI must state the assumption next to the range.
- Program preferences: `filterPrograms(profile, programs, now)` returns `{ kept, excluded: [{ programSlug, mismatches }] }` and hides a program only on a definite mismatch (destination, field, institution type, study language). Unknown, stale or non-official teaching-language data never hides a program. Excluded programs are returned with reasons so the UI can offer to show them. Budget is not a filter.
- Scholarships: `scholarshipsForProgram` applies the nationality filter to every result, including scholarships linked from `program.scholarships`.
- Checklist: the ten steps from the spec in fixed order (documents → translation → language exam → application account → submit → scholarships → financial documents → accommodation → visa → departure). Inapplicable steps are marked skipped with a reason, not dropped.
- Checklist takes the real `match` result. `language_exam` is skipped only when the student's certificate is accepted AND the level meets the requirement AND every language reason (including route conditions) passed and the route conditions were actually evaluated, i.e. route `direct` or `check` (`certificate_held`), or when the source states no language rule and the route was actually evaluated (`not_required_by_source`). `application_account` is skipped (`no_account_required`) only when the channel says no account is required with a decisive channel fact AND the program→channel link is decisive AND the supplied channel's slug equals it. Unknown or stale data never produces a skipped step.
- Country-specific application channels (national portals, uni-assist, Studielink, Campus France…) are data on the route/program, not code branches.
